# Claude question control codec sources and boundary

This module only decodes and encodes Claude Code 2.1.196 control JSON. It does not launch a CLI, send bytes, grant permission, create a C card, or settle an answer.

## Fixed official source

- [Anthropic Agent SDK 0.3.196 npm package](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.196.tgz), metadata `claudeCodeVersion=2.1.196`, integrity `sha512-yqsp1/04T2/tJ54jz+7YLsTZOPeQ/myUCrv17/IVZ9dbl+izIMP9ULuLpPCH5pj5msXxR80es+hpVgHoFuNm0A==`. In `sdk.d.ts`, `SDKControlRequest` has outer `request_id`; `SDKControlPermissionRequest` has `subtype=can_use_tool`, `tool_name`, `input`, and `tool_use_id`. In the published `sdk.mjs`, `processControlRequest` passes the original tool-use ID to `canUseTool`, adds `toolUseID` to its returned decision, and `handleControlRequest` writes a `control_response` with `subtype=success`, the same `request_id`, and that decision as `response`. Those spellings come from the fixed SDK code, not the historical seat wrapper.
- In the same package, `sdk-tools.d.ts` gives `AskUserQuestionInput.questions` (1–4) with `question`, `header`, `options` (2–4 `label`/`description`, optional `preview`), and `multiSelect`. Its output keys answers by the original question text. The question array has no per-question vendor ID. This codec's `host_index` is derived from the array position and is never sent as a vendor identifier.
- [Anthropic fixed Windows CLI 2.1.196 npm package](https://registry.npmjs.org/@anthropic-ai/claude-code-win32-x64/-/claude-code-win32-x64-2.1.196.tgz), integrity `sha512-Jz3R4pBXh48COCvumeykQPJXF9Dc1E7n9KeajAEKsHyj2WmgkR0GBXY0g/XBd1xtNono4CQjzaqXdEXa1Xqoog==`. Static reading of its published bytes shows `AskUserQuestion` requires interaction, asks permission, and consumes `answers` in its original tool call. The binary also contains a `permission_ask_user_question` dialog path. Static code does not qualify which path the product's exact launch arguments actually emit, so `request_user_dialog` is explicitly unsupported here.
- Current [Anthropic Agent SDK user-input guide](https://code.claude.com/docs/en/agent-sdk/user-input) describes the `canUseTool` AskUserQuestion path and answering with original `questions` plus `answers` keyed by question text. It is current documentation, not a captured fixed-version transcript.

## Existing product and historical reference

- Historical `packages/seat-runtime/src/claude-seat.ts` used `--permission-prompt-tool stdio`, an original `control_request.request_id`, and a same-process `control_response`. That implementation generated ordinal UI IDs and did not establish a fixed 2.1.196 product receipt.
- `provider_evidence/stream_json.rs` bounds frame/depth and recognizes generic control requests. `normalize.rs` leaves them unhandled. The M2 native output branch now raises only exact Claude `AskUserQuestion` frames; `launch.rs` adds the fixed `--permission-prompt-tool stdio` argument without changing the CLI pin or the independent HOME/APPDATA placement.

The positive decoder accepts only `control_request` / `can_use_tool` / exact `AskUserQuestion` with both original IDs and a nonambiguous full question array. Other tool approvals return `None`; a `request_user_dialog` with `dialog_kind=permission_ask_user_question` returns `Unsupported` because its answer result is not qualified. The answer encoder preserves every original input field, adds answers keyed by the exact original question texts, and emits the fixed SDK control response with the same outer request ID and `toolUseID`. It accepts free text exactly as supplied and requires one answer for each original question. Neither encoding nor a successful stdin write proves Claude accepted the answer; A/H must observe the original tool result or terminal evidence in the same process and turn. Actual CLI branch, answer acceptance, and Windows behavior remain **NOT_RUN**.

## Native C/H binding added in M2

The fixed CLI launch adds only `--permission-prompt-tool stdio`; the pinned CLI, safe mode, model, and HOME/APPDATA placement remain as before. C raises a Claude card only from A's original exact `AskUserQuestion` control request while the same H send is still pending and the physical process/Owner/E/seat binding is live. The card's `turn_id` is explicitly the original H **host** User send `request_id`, since Claude 2.1.196 supplies no native turn ID in the control request. `vendor_thread_id` is the real `system/init` or original echoed-User `session_id`; `vendor_item_id` is the original tool-use ID. The existing C request column stores the original Claude `request_id` as a canonical JSON string scalar, matching that column's request identity contract; the original unquoted spelling remains in the A frame. C's source descriptor preserves A's operation/epoch/cursor/frame SHA-256. The complete original input is in the card's `question_payload.originalInput`, and the original A frame remains the source of truth.

`question_payload.questions` exposes every question with `hostIndex`, `hostQuestionId` (`host0`, `host1`, ...), `multiSelect`, and original options with `hostOptionId` (`option0`, ...), label, description, optional preview. `idOrigin=HOST_DERIVED_ARRAY_INDEX` says these are product IDs, not vendor IDs. User `answers` keys are those `hostQuestionId`s, with arrays of original labels or a single free-text Other value. The fixed SDK input/output types specify `answers` keyed by original question text and a string value, including comma-separated multiple selections; the historical `packages/seat-runtime/src/claude-seat.ts` used `answers.join(", ")` at line 450. The M2 encoder uses that spelling in original User array order. Multiple selected labels containing commas are rejected because they cannot be represented unambiguously in that string; the original User request remains retained. This is a static source-based codec choice, **not** a golden observed 2.1.196 transcript.

After C commits the exact User answer intent, H checks the original C/A source, the exact answer frame, the original H User send and its A echoed UUID/text/session before the question cursor, same custody and real A `system/init` session, then records a no-ACK `control_response` step before the sole stdin writer. `WRITTEN` proves only the exact pipe write; C's `ANSWERED` settlement uses that typed H step and does not claim vendor consumption. UNKNOWN is readback only. A later original pure `tool_result` with the same tool-use ID and vendor session, or an original H result receipt that cites the exact terminal raw source, can expire an OPEN card; neither overwrites an answer already in flight. `request_user_dialog` and ordinary tool permissions remain outside this path. Native compilation, actual CLI/model turn, Owner Win11/SAC, and E2E are **NOT_RUN** for this M2 source change.

## Captured-batch ordering repair

The native reader can capture up to 32 A frames before product projection. An unbounded H scan over that whole captured batch could commit a later Claude Result and clear `pending_claude` before C raised an earlier `AskUserQuestion`; the earlier raw frame then remained PENDING because C no longer had the original H send identity. The falsifying check is the original A cursor sequence and H/C durable order: a question cursor before a Result cursor must be raised before that Result consumes the send. H now advances only through the cursor C is about to handle. The echo establishes the real session and original User send first, C processes a question or pure tool-result at its own cursor, and only the Result cursor commits the original H receipt and expires still-OPEN cards. A no-write historical H receipt readback reconciles an already committed Result after earlier C frames have been projected. It never resends a User or question answer, and it leaves `ANSWER_UNKNOWN` unresolved. Actual CLI/model and installed Win11 behavior remain **NOT_RUN** until the real candidate and immutable reader run.
