# Claude question control codec sources and boundary

This module only decodes and encodes Claude Code 2.1.196 control JSON. It does not launch a CLI, send bytes, grant permission, create a C card, or settle an answer.

## Fixed official source

- [Anthropic Agent SDK 0.3.196 npm package](https://registry.npmjs.org/@anthropic-ai/claude-agent-sdk/-/claude-agent-sdk-0.3.196.tgz), metadata `claudeCodeVersion=2.1.196`, integrity `sha512-yqsp1/04T2/tJ54jz+7YLsTZOPeQ/myUCrv17/IVZ9dbl+izIMP9ULuLpPCH5pj5msXxR80es+hpVgHoFuNm0A==`. In `sdk.d.ts`, `SDKControlRequest` has outer `request_id`; `SDKControlPermissionRequest` has `subtype=can_use_tool`, `tool_name`, `input`, and `tool_use_id`. In the published `sdk.mjs`, `processControlRequest` passes the original tool-use ID to `canUseTool`, adds `toolUseID` to its returned decision, and `handleControlRequest` writes a `control_response` with `subtype=success`, the same `request_id`, and that decision as `response`. Those spellings come from the fixed SDK code, not the historical seat wrapper.
- In the same package, `sdk-tools.d.ts` gives `AskUserQuestionInput.questions` (1–4) with `question`, `header`, `options` (2–4 `label`/`description`, optional `preview`), and `multiSelect`. Its output keys answers by the original question text. The question array has no per-question vendor ID. This codec's `host_index` is derived from the array position and is never sent as a vendor identifier.
- [Anthropic fixed Windows CLI 2.1.196 npm package](https://registry.npmjs.org/@anthropic-ai/claude-code-win32-x64/-/claude-code-win32-x64-2.1.196.tgz), integrity `sha512-Jz3R4pBXh48COCvumeykQPJXF9Dc1E7n9KeajAEKsHyj2WmgkR0GBXY0g/XBd1xtNono4CQjzaqXdEXa1Xqoog==`. Static reading of its published bytes shows `AskUserQuestion` requires interaction, asks permission, and consumes `answers` in its original tool call. The binary also contains a `permission_ask_user_question` dialog path. Static code does not qualify which path the product's exact launch arguments actually emit, so `request_user_dialog` is explicitly unsupported here.
- Current [Anthropic Agent SDK user-input guide](https://code.claude.com/docs/en/agent-sdk/user-input) describes the `canUseTool` AskUserQuestion path and answering with original `questions` plus `answers` keyed by question text. It is current documentation, not a captured fixed-version transcript.

## Existing product and historical reference

- Historical `packages/seat-runtime/src/claude-seat.ts` used `--permission-prompt-tool stdio`, an original `control_request.request_id`, and a same-process `control_response`. That implementation generated ordinal UI IDs and did not establish a fixed 2.1.196 product receipt.
- The current `provider_evidence/stream_json.rs` bounds frame/depth and recognizes generic control requests. `normalize.rs` leaves them unhandled. `product_database/v37_output.rs` only raises the existing native C question card for Codex. The current Claude launch recipe in `provider_evidence/commands.rs` does not request the stdio permission host. These are shared integration gaps owned outside this codec.

The positive decoder accepts only `control_request` / `can_use_tool` / exact `AskUserQuestion` with both original IDs and a nonambiguous full question array. Other tool approvals return `None`; a `request_user_dialog` with `dialog_kind=permission_ask_user_question` returns `Unsupported` because its answer result is not qualified. The answer encoder preserves every original input field, adds answers keyed by the exact original question texts, and emits the fixed SDK control response with the same outer request ID and `toolUseID`. It accepts free text exactly as supplied and requires one answer for each original question. Neither encoding nor a successful stdin write proves Claude accepted the answer; A/H must observe the original tool result or terminal evidence in the same process and turn. Actual CLI branch, answer acceptance, and Windows behavior remain **NOT_RUN**.
