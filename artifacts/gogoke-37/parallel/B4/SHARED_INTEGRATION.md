Phase: `B4.1` / M2. Work package scope is Grok ACP protocol behavior only. This note is an integration handoff, not a shared-contract change or acceptance record.

- Product pin: Grok Build CLI `1.0.41`. The installed public CLI reported `grok 1.0.41 (4220f3b224a6)`. The source-audit snapshot separately pins the public repository at `b13fa526f5112c0b20dad5f1f2300d3d3b127895`, whose `SOURCE_REV` was `a51a1dc62fe20029ac39a665985bba78edbb870f`. - A no-login ACP probe observed `initialize` protocol version 1, `agentVersion` 1.0.41, `loadSession=true`, and advertised `list`, `resume`, and `close` session capabilities. An unauthenticated `session/new` returned JSON-RPC error `-32000 Authentication required`; no `authenticate`, browser, prompt, or model request was sent. The sanitized initialize/setup/auth-denial excerpt is embedded in `protocol.golden.test.ts`.
- Capability declarations are reported separately from methods that returned a successful response. The report keeps load/resume advertised, and cancel, steer, native question cards, effective memory-off, and cross-project memory isolation unqualified until actual pinned-version evidence exists.
- During a read-only `grok inspect --json` probe, only `GROK_HOME` was isolated; inherited `HOME` and `USERPROFILE` were not. The CLI reported one enabled Claude-compatible instruction source whose path was outside the current working directory. The probe ran from the construction worktree and did not send a model prompt. Its path was not compared with H's permitted physical roots, and `inspect` output does not prove an LPAC process could read or a model session consumed it. This is an incomplete environment observation, not a boundary violation or isolation result.

## Host wiring required

1. H must resolve and pin the executable from the native instance registry, verify its measured digest/version, create the process suspended, and inspect the actual child token, image, directory identities, and Job membership before resume. LPAC is required for every model session. An LPAC admission failure is a hard refusal; there is no ordinary-user process fallback.
2. Pass an explicit child environment with `HOME`, `USERPROFILE`, and `GROK_HOME` rooted in the registered instance area, project `cwd`, and only approved environment values. Strip inherited host home/config selectors and secret-shaped values. Before classifying any discovered path, compare its canonical physical identity with H's allowed roots. The adapter does not read or copy `auth.json`, and its TypeScript state is not an LPAC authorization proof.
3. Spawn the public ACP entry as `grok agent --no-leader stdio`. Do not use `--always-approve`, `--reauth`, device authentication, a user-profile fallback, or the separate `-p`/streaming-json path. Start requests use an empty MCP list and `_meta.yoloMode=false`.
4. For the Owner-authorized M2 login touchpoint, the historical GOGO PARTY `PROVIDER_LOGIN` entry uses `grok login --oauth`; the official CLI documents `grok login` as browser OAuth by default and `--device-auth` for headless login. Login remains an Owner-only visible-browser action. H/F must let the vendor CLI own its credential files and only report bounded status; never read, copy, log, or put credential bytes in evidence. GOGO PARTY's historical status probe is `grok models` with three-way matching: `logged in with` means ready, `not authenticated` means logged out, and neither means unknown. That historical behavior is reference only, not proof for this pinned instance.
5. Current official configuration docs describe `GROK_MEMORY=0` and `[memory] enabled=false`; this package did not establish their effective behavior in the pinned 1.0.41 process. They may be requested in the explicit launch environment or instance config, but memory must remain `NOT_RUN` until H/A collect actual prompt/input evidence, inspect the vendor memory store without exposing contents, and run the M2 cross-project marker case. Startup, `inspect`, a requested setting, or a model self-report is not memory-off evidence.
6. Current official project-rule/config docs say Claude compatibility defaults on and can be disabled per surface with `[compat.claude] agents=false` and `rules=false`; rules and named instruction files are separate surfaces. Cursor has analogous `agents`/`rules` fields. The documented `GROK_CONFIG` overlay currently permits only a narrow setting allowlist and cannot be assumed to carry `[compat.*]` changes. `$GROK_HOME/rules/` is always scanned. Confirm which of these settings exist in pinned 1.0.41 before relying on them; write any approved instance config only under the registered `GROK_HOME`. Verify with the exact pinned CLI at the registered project `cwd`, the actual H allow-root list, and the real LPAC token. If H cannot enforce or observe the boundary, report `UNSUPPORTED`/`NOT_RUN`.

## Transport and receipt behavior

The expected sequence is ACP `initialize` response with version/capability check, then `session/new` with the project `cwd` and empty MCP list, then `session/prompt`. This ordering matches the official agent-mode guide and the measured no-login probe: `initialize` completed before `session/new` was attempted. The probe could not qualify successful `session/new` or first prompt, so those remain unproven until OT4 and an isolated LPAC run. The adapter consumes H's already-authorized ACP transport and never creates a child process. It also supports `session/load` on a fresh initialized transport to reconcile an existing native session ID; a lost response does not create a new session ID or replay a prompt.

Raw vendor notifications stay tagged `grok-build` for A to filter and normalize; thought, auth, usage, session transcripts, and account metadata must not be copied to public artifacts.

Grok ACP has no qualified in-turn steer in the current evidence. `interruptAndResume` sends `session/cancel`, waits for the original `session/prompt` response to explicitly settle as `stopReason=cancelled`, then sends the replacement prompt to the same session. Its receipt names that terminal stop reason and the replacement prompt's actual response. If transport outcome is lost, the old turn does not confirm cancellation, or the terminal reason is anything else, the adapter sends no replacement and enters recovery-required/unknown. A notification write is not a cancellation receipt.
