- 需要 Owner 二选一：
  - 执行一次采用：开 PR，Owner 本人合并，产品回读；

### F2 中：updateRef 被拒后，写入操作永久卡在 OUTCOME_UNKNOWN，没有恢复路径

- 位置：`third_party/t3code/apps/server/src/gogoke/context/repository/gitFactWrite.ts`，以及 `apps/desktop/native-host/src/store/authority/r2_fact_journal.rs`。
- 过程：
  1. `writeR2TestFact` 在 `updateRef` 之前，先经 `bindTarget` 把 `(base_head, target_commit)` 永久写入 native journal。
  2. 如果 `readHead` 与 `updateRef` 之间有其他写入者推进了测试分支，`PATCH … force:false` 会被拒（非快进）。
  3. 随后 `verifyBound` 发现 target 不在分支上，抛出 `TEST_FACT_WRITE_OUTCOME_UNKNOWN`。
- 被卡住的原因：
  - `operationId` 由 `actionCompletionRef` 与 `executionEvidenceSha` 确定性派生，重试时 `begin` 返回已绑定的条目，直接走 `verifyBound`，永远得到同一个错误。
  - `bind` 拒绝任何不同的 target，而 journal 没有重新绑定或作废的路径。
  - 结果：这份结果再也发不出去。
- 可能性：同机并发已被 root 锁挡住。但这个分支历史上有过其他写入者（`1ee82a27`、`e1df8787`），跨机器或手工写入时会触发。
- 建议：
  - 把 `updateRef` 明确被拒（422 非快进），且回读确认 target 不在分支上的情况，判为确定失败，而不是结果未知；
  - 允许 journal 在这种情况下以新的 base 重新绑定，或作废后重来；
  - 补一条测试：模拟"读头之后分支被推进"。

### F4 低：`spawnSync("gh")` 按名称解析

- 只有同一用户下的攻击者能利用，影响低。
- 可以改为先解析出绝对路径再调用。
