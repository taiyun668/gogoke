# GOGO PARTY 停止条件设计

## 背景

GOGO PARTY 是本地优先的多 Agent 项目房间。一个项目 = 一个群聊房间，
人和多个 worker 都是「席位」，任何席位可 `@` 任何席位，没有固定流程，
`@` 就是调度器。材料走 git 仓库，不走聊天。已实现并验证：

- 持久隔离席位（每席位独立 HOME、独立会话、transcript 留存）
- 席位互相 `@` 自动接力，无人搬运
- 交接的是仓库引用而非正文；commit 由房间代做，席位**没有 git 权限**
- 房间每轮计算 `material = {baseCommit, headCommit, commits[], changedFiles[]}`
- 审计席强制只读；已按 providerFamily 判定审计独立性
- 一条回复可 `@` 多个席位，触发扇出，形成回复树

## Owner 的性质（硬约束）

Owner 不写代码。他能判断「这是不是我要的方向 / 结果」，
不能判断「这段 commit 质量如何 / 这算不算真进展 / 这个权限给了会怎样」。

## 已定哲学（不可推翻）

默认自动，例外才停。系统仅在四种情况下找 Owner：
1. 不可逆且有真实代价的动作
2. 低级空转
3. 段落级价值对账
4. Owner 主动喊停

## 被否决的前身

`maxAgentHops = 4`：跳数量的是委派深度，不是是否推进。
长跑项目被反复打断，3 跳就死的循环却能空转满 4 轮。已移除，目前无替代：
深度无界 × 扇出宽度无界 × 每节点一次付费模型调用。

# 设计

## 零号规则：能力边界不可由对话推翻

以下属于产品层常量，**任何席位的任何请求都硬拒绝，不生成授权卡、不打扰 Owner**：

- 审计席只读
- 席位的 git 权限（永远没有；commit 由房间代做）
- 席位的工具能力集、沙箱等级、可写路径
- 席位自身的 provider / 模型 / family

被拒绝的请求记入该席位的诊断记录，并按规则二计为**无进展**。

理由：规则三「我核对过，非自述」的全部可信度建立在审计席只读之上。
若这堵墙可以被一次 Owner 点击拆掉，而 Owner 判断不了拆掉的后果，
则该墙形同虚设。此类变更属于不可逆控制面代价，不适合走「找 Owner 批准」。
真要变更，只能由 Owner 在房间之外主动修改配置文件，不能由席位在对话内发起。

## 规则一：不可路由的 `@` 是噪音，不是授权通道

`@` 到不存在的席位：记日志，在时间线里折叠成一条通知，不静默丢弃。

- **没有 `[批准]`。** 选项只有 `[忽略并折叠]` 和 `[让某个可路由席位看这句话]`
- 命中零号规则的请求：自动拒绝，不出现在 Owner 面前
- 同一对话、同一非法收件人**折叠为一条**；超过 N 次不再打断 Owner，
  改为**计入规则二的无进展**
- **处理规则一卡片的人类操作不触发规则二回满**

## 规则二：进展续命的接力配额

按对话计一个计数器，默认上限 5（可配）：

- 每次**自动**触发席位调用：−1
- 发生「进展事件」：回满
- 归零：该对话**闩锁暂停**，直到 Owner 显式继续

### 进展事件只有一种

**实质性新材料**：房间替施工席落下的 commit，且该 commit 通过实质性检查。

实质性检查（房间已有 `changedFiles[]`，直接复用）：
- 空 diff → 不算
- 纯空白 / 纯格式 / 纯注释变更 → 不算
- 无文件路径变化的 commit → 不算

不通过检查的 commit 不回满，计数器继续朝零走。

### 明确不算进展的东西

- **审计席的 PASS / FAIL 不算。** 裁决属于对账，不属于续命。
  同一 HEAD 的首次裁决只用于规则三叙事与审计状态机。
- 规则一的路由噪音不算
- 归零诊断本身不算

### 人类回满的收窄定义

只有两种人类动作回满：
1. Owner 在**本对话**对规则二/三/四的卡片点 `[继续]`
2. Owner 发出新的方向句

`[拒绝]`、`[忽略]`、处理路由噪音、`[让审计席细说]` 追问，**都不回满**。

### 扇出

余量不足时拒绝超额 `@`：只触发余量个席位并立刻归零。
禁止单条消息把计数器打成任意负值仍全量开火。

### 归零诊断

归零时派一次（且仅一次）诊断给审计席，用人话说清卡在哪、谁的问题、有几条出路。
诊断调用：**不计进展、不可 `@` 任何人、不可落材料、不解除闩锁**。
诊断失败则带失败译文直接给 Owner。
Owner 说继续后再次归零，第二次不再派诊断，直接到 Owner。

## 规则三：对账检查点

房间记住 Owner 最后过目的 commit（checkpoint ref）。

**触发条件（任一满足）**：
- 自 checkpoint 起未过目材料超过体量阈值（如 10 个实质性 commit 或 30 个文件）
- 距 Owner 上次过目超过墙钟时间阈值（如 4 小时）

体量与时间双维度：避免高密度废 commit 在几分钟内烧完窗口，
也避免极慢项目永远不对账。

**流程**：当前轮结束后闩锁暂停 → 自动派审计席做段落审计 → 产出 Owner 卡片。

**审计席的取证范围**：只认仓库 diff（`checkpoint..HEAD`）与目标锚点。
**不得**把施工席在本窗口内对它发出的自述性 `@` 当作证据。

**卡片必须并排给出两栏，让 Owner 判的是「两者的差」，而不是审计席替他下的结论**：

```
你当初说的：<原文引用目标锚点>

施工席声称做到的（原文引用它自己的话）：
  ...

审计席核对仓库后确认的：
  ✓ ...（有 diff 佐证）
  ✗ ...（声称但仓库里没有）

审计席的建议（仅供参考，不是结论）：<是否偏离>

下一段打算：...

[继续]  [停一下]  [方向要改]  [让审计席细说第 N 条]
```

**checkpoint 前移规则**：
- `[继续]` → 前移
- `[方向要改]` → **必须先由 Owner 给出新锚点一句话**，然后前移
- `[停一下]` → 不前移
- `[让审计席细说]` → 不前移

## 规则四：花费闸门

每对话、每天各一条成本上限。上限由 Owner 设定或确认；系统默认值只是未确认前的保守值。

**所有付费调用计入同一上限**：席位工作、规则二诊断、规则三审计，无例外。
触顶后不得再开任何一次付费调用——若诊断尚未派出而已触顶，跳过诊断，直接给花费卡。

触顶时闩锁暂停，卡片翻译成人话（「本对话今天已花掉你定的上限」），不抛 token 流水。
选项仅 `[加预算并继续]` `[停]`。

## 规则五：Owner 主动喊停

Owner 在任何时刻可对任一对话或全房间发出停止。
立即闩锁：不再发起新的席位调用；已在途的调用跑完当前轮后停在那里，不触发接力。
恢复需要 Owner 显式动作。

## 目标锚点

每个对话存一句 Owner 的原始方向句，作为规则三的对齐基准。

**合格性检查**：开场句若过短、纯寒暄、纯「开始吧」，不能作为锚点。
此时先向 Owner 要一句锚点，**未拿到之前不进入自动接力**。

**更新协议（只有两条路）**：
1. Owner 发出新的方向句
2. 规则三点 `[方向要改]` 并提交新一句

更新后以新锚点为准，旧锚点保留为历史。
**规则二的人类回满不等于锚点更新。**

# 与四种停止条件的映射（如实陈述，非一一对应）

| 停止条件 | 实现 |
|---|---|
| 1 不可逆且有真实代价 | 零号规则（能力边界硬拒绝）+ 规则四（花费）。**两半分开实现，不由规则四兼管权限** |
| 2 低级空转 | 规则二 |
| 3 段落级价值对账 | 规则三 + 目标锚点 |
| 4 Owner 主动喊停 | 规则五 |
| （非停止条件） | 规则一：路由失败的噪音处理，**不是找 Owner 的第五种理由** |

# 统一原则

送到 Owner 面前的任何东西，必须已被翻译成他能判断的形式，并且带可执行选项。
Owner 只做**方向裁决**和**花费授权**；不做技术裁决，不做权限授权。

# 机器与 Owner 的分工（精确陈述）

机器**确实**做了两个预判，这不是「不做判断」：
- 什么算「实质性材料」（机械规则：空 diff / 纯格式 / 无路径变化）
- 何时该对账（机械阈值：体量 + 时间）

机器**不**做的：
- 材料的方向对不对
- 这一段做的东西值不值

审计席做技术核对并翻译，但其结论在规则三卡片上标为**建议**，
Owner 判的是「声称」与「实际」两栏的差。

# 已知缺口（自陈）

1. 单一审计席仍是译文单点。M7 隔离 provider family，但不隔离仓库投毒、
   对话框架效应、译文垄断。当前缓解只有「只认 diff + 锚点」这一条反污染。
2. 一条各轮都产出「实质性但方向错误」材料的链：规则二不拦，
   规则三要等阈值才摊开。时间阈值缩短了这个窗口但没有消除它。
3. 「纯格式 / 纯注释」的判定本身可被绕过（例如每轮加一行有语义的废代码）。
   这是实质性检查的下界，不是终点。

# 请审计的问题

1. 规则二的「实质性新材料」能否被低成本博弈？给出具体、可执行的最省力攻击路径与买到的轮数。
2. 零号规则把能力边界移出授权流之后，还有没有别的路径能让席位扩权或削弱审计独立性？
3. 规则一改成无 `[批准]` 之后，还能不能被当作噪音通道或续命通道使用？
4. 规则二的「人类回满收窄」是否仍有可被席位诱导的人类动作？
5. 规则三的两栏卡片是否真的把判断权还给了 Owner，还是只是把结论换了个位置？
6. 规则四「所有调用计入同一上限」与规则二/三的闩锁之间，有无死锁或饿死？
7. 目标锚点的更新协议是否存在被席位诱导改写的路径？
8. 逐条给 SOUND / SOUND-WITH-PATCH / UNSOUND，不合格的给最小补丁。
9. 自陈的三条已知缺口之外，有没有未被自陈的更严重缺口？
10. 整套设计最危险的一条是什么，为什么是它。
