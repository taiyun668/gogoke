## 二、必须先定的三件事

这三条排在 S1 之前。不是因为难，是因为**做到一半再回头改会推翻前面的工作**。

### ① 进程模型 —— 计划里最大的空白

`packages/room` 与 Rust 内核之间**目前一根线都没有**：没有 FFI、没有 napi、
没有 sqlite 依赖，房间数据落在 `timeline.json`。

而 S2「Room 接入」被写成一个步骤。它首先要回答的其实是：

- 同进程 FFI（napi-rs）？
- 内核作为子进程 + 本地 socket？
- 内核作为独立常驻服务？

这个选择会反过来改写 **S3**（重启恢复、进程身份放在哪一侧）和
**S6**（关掉界面后谁还活着）。

**它是唯一一个改起来会推翻前面工作的决定，却没有出现在「不能颠倒的硬门」里。**
建议提到 S0，与「产品语义收敛」并列。

### ② `room_id` 进不进 schema

`project_id` 在迁移文件里出现 **278 次**，`room_id` 出现 **0 次**。

而 G1 写的是「所有写入必须带 `project_id + room_id`，数据库层强制项目隔离」。
房间这一半在数据库里根本不存在。

「项目 ≠ 房间」是产品的核心概念（项目是总上下文，房间是项目里某个板块的
上下文）。当前 schema 只认项目。

**这不是接线工作，是 schema 变更加迁移。** G1 把它写成一句话带过，
而它实际上是 G1 里最大的一块。

建议：进。否则 WorkThread 无法回答「这条工作链属于哪个房间」，
而时间线是按房间分的。

### ③ 实例独占归 Store 还是归 Room

Run 要绑 CLI 实例。而实例池现在是**全局的、跨项目的**，独占闸由 Room 保证
（`server.ts` 的 `instanceStore.claim`）。

一旦 Store 成为「唯一状态权威」，这条约束归谁？

- 两边都保证 → 必然漂移，且漂移时没人报错
- 都不保证 → 直接漏

建议：**归 Store**。Run 已经在那儿了，而这条约束的后果是最严重的一类
（一份凭据两个活进程，refresh token 轮转互踢）。

> 补充：这条闸刚刚经过一轮加固，有现成的东西可以直接搬过去 ——
> `packages/room/src/proc.ts` 的 `processStartedAt` / `isSameProcess`，
> 以及 `instances.ts` 里孤儿占用的判定（pid + 创建时间成对，
> 单独一个 pid 不作数）。见 §三之 ⑥。

## 三、其余问题（不阻塞，但要写进计划）

### ④ `conversationId` 现在不是「稳定的工作链 id」

代码是 `message.conversationId = message.id` —— **它就是第一条消息的 id**。
人在同一件事上再补一句话，就是一个新的 conversationId、一条新的 WorkThread。

而整份计划的核心主张是「工作链由自然对话形成」。要成立，必须回答
**后续消息怎么并进同一条链**：

- 靠回复关系（replyToId 溯源到同一根）？
- 靠 @ 同一个席位？
- 还是由人显式说「接着刚才那个」？

计划把这条当成已有能力，实际上它是这个主张能不能成立的那个点。

### ⑤ 六种状态少了一种：环境不具备

实例被上一轮房间残留的进程占着时，Run 起不来。它既不是「正在工作」，
也不是「已停止」。

塞进「状态待确认」会把一个**有明确出路**的情形（去结束那个进程，
界面已经会报出进程号），变成一个听起来要人去查的情形。

### ⑥ 「进程身份」排在 S3 太晚

S1/S2 一旦有了原子派发，重启恢复时立刻就要判断「上一轮那个 Run 是不是
还活着」—— 那就需要 pid 加创建时间。

这块已经实现并经过真机验证：房间被强杀之后，它启动的 `grok.exe` 仍然活着、
pid 与创建时间都没变；新一轮启动如实拒绝把实例交出去。

顺序上它属于 **S1**，不是 S3。

### ⑦ 「已完成」的判据有个洞

「需要修改仓库的任务已取得提交/文件等成果证据」——
但现有代码在接力时明确把「什么都没留下」当成**一个发现**，不是失败
（审计席看完说没问题，本来就没有仓库改动）。

这种 Run 怎么进终态，计划没写。

### ⑧ legacy timeline 导入后怎么显示

「不能倒推它们已经可靠完成」方向对。但导入后旧数据在 UI 上显示成什么？
如果一律「状态待确认」，人一打开就看到满屏待处理项 —— 那和没导入一样糟。

建议：旧数据单独一类「历史记录（无运行证据）」，不进任何待办计数。

### ⑨ ContextSnapshot 要记「排除了什么」

「哪些内容因隔离策略没有提供」要显示给用户 —— 这是好设计。

但它要求 snapshot 记录**被排除的内容**，而不只是被包含的。
实现时很容易退化成只记「包含了什么」，那条界面就永远是空的。
建议在接口冻结时把这个字段设成必填。

## 四、结论

**方向同意**：不另造任务模式、内化而不是重建、Store 作为唯一权威、
CLI 说「完成了」不算数。最后一条尤其对 —— 这正是最近反复踩到的那类问题
（「关闭成功」其实没关掉，进程还活着占着凭据）。

**建议的修改**：把 §二 的三条提到 S0，与「产品语义收敛」并列。
其余按原顺序推进。
