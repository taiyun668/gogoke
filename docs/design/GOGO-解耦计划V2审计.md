## 一、我错了三处，它是对的

这三条我要先认，因为其中一条会改变五家适配的工作量估计。

### 1. Antigravity 只能一次性 —— 我错了

我在交给它审计时自己标了"依据只是 AionUi 的源码注释，本机没装 agy"。V2 的 A05 说不能把不可靠的判断变成约束，并引官方文档。

**我去查了官方文档，它是对的**（https://www.antigravity.google/docs/cli/headless/）：

- `--continue` / `--conversation <id>` 能续接上下文，但文档明说 **"Each of these starts a new process."**
- `--input-format stream-json` 则是 **"maintain a single, continuous conversation process, feeding it prompts one by one on stdin. Each prompt executes a full turn and emits its own result event."** 还特意说明"进程只启动一次，后续回合跳过启动开销，复用热好的会话"。

也就是说 **`agy` 支持常驻多轮，形状和 Claude Code 的 `--input-format stream-json` 基本一样。** 我那条"只能当一次性席位"的结论撤回。

补一句 V2 也说了的、而且是我自己老 GOGO 记过的教训：**这是官方网页，不是本机 `agy --help`。** 而且 agy 本机没装。所以正确状态是"文档记载支持常驻，实装能力待验"，不是"已确认支持"。

还有一个对合同有影响的细节，V2 的 X12 抓到了而我没有：`result` 事件里的 `num_turns` 是**整段会话的用户回合数**，不是本轮增量。常驻多轮模式下按行累加用量会算错。

### 2. 隔离测试"已实现且已有断言" —— 我说过头了

V2 的 X02 说：Claude 席位有自己独立的 `isolatedEnv`，而 `isolation.test.ts` 主要断言的是公共的 `buildIsolatedEnv`，其中 Grok 那条还是**源码字符串匹配**。

回源核对，**全对**：

- `claude-seat.ts:102` 有一个私有的 `isolatedEnv(home)`，在 `:228` 处 spawn 时使用 —— **它不走公共收口。**
- `isolation.test.ts` 最后那条 "Grok 席位确实走收口" 是 `readFileSync` 读 `grok-acp-seat.ts` 的源码文本，剥掉注释后正则匹配 `env: buildIsolatedEnv(`。**这证明的是代码长什么样，不是进程跑起来环境是什么。**

所以准确的说法是：**公共 helper 的规则测得很扎实（四维家目录、密钥、端点、extra 逃逸都有反例），但"每一次真实 spawn 都受这套规则保护"没有被证明。** 我把前者当成了后者。V2 的 §0.1 专门立了证据分层（需求记录／签名／源码行为／测试存在／本次通过／真实运行），我这条正好是拿"测试存在"冒充了"真实运行"。

它还顺手抓到一条我读过那个文件却没看出来的：测试里 `DATABASE_URL: "postgres://x"` 和 `HTTP_PROXY` 被当作"正常变量不能被误伤"放行。**反例本身是对的**（把代理全断了比漏一个变量更难查），**但 `DATABASE_URL` 里通常就带着密码。** 按名字判断有没有秘密不成立 —— 这条 X03 提得准。

### 3. 迁移缺"更新状态" —— 半对，措辞会造成后门

我说迁移盘点漏了自更新状态与白名单。V2 的 A16 说白名单和公钥属于发布代码，不是可由旧用户数据覆盖的配置。

核对 `gogoke_update.rs`：`ALLOWED_HOSTS` 是 `const &[&str]` 编译进去的，`RELEASE_PUBLIC_KEY` 是 `include_str!`。**它是对的。** `PreparedUpdateState` 那类运行数据确实要迁（V2 §10.1 已补），但如果照我的说法建一条"从旧库导入允许主机"的路径，那就是**供应链后门**。这个纠正比我的原意见更重要。

## 二、它找到了四处我没扫到的，两处是安全缺口

这四条是 V2 最值钱的部分，全部回源核对属实。

| | 事实 | 后果 |

## 四、V2 自己的四个问题

### 4.1 它犯了刚修好的那类错：WP03 的四个测试要等 WP09a

依赖图是 `WP03 → WP09a`（WP09a 依赖 WP03）。但 WP03 名下九个测试里有四个需要 WP09a 的产出：

| 测试 | 要什么 | 谁产出 |
|---|---|---|
| T21 | "read-only 真实约束成立；**无等价原生／OS限制**时不扩成 full access" | 要知道"有没有等价"，得先探测 → WP09a |
| T31 | "同官方登录多配置并行**符合实际能力**" | 实际能力 → WP09a |
| T50 | "**每家**实际 spawn 的 env/cwd/home/端点/钩子逐维度负测" | 每家 = 五个二进制的位置与版本 → WP09a |
| T51 | "不同 profile/**authRevision**/隐私域不误复用连接" | authRevision → WP09a 交付"认证配置版本" |

而 WP03 自己的验收写的是「假原生进程链可运行……**真实 CLI 的综合能力留给 WP11**」。**验收范围声明是假件，名下测试要真实五家。**

这正是 V2 接受 A08 时命名的那个东西 ——「**验收条件形成的隐含环**」。它修了我找到的两处，自己留了第三处。

更值得说的是：**V2 自己的 T61 就能抓住它** ——「依赖图无环；每测试一个主责；**每消费项有前置产出**」。T61 主责是 WP01（第 1 层），跑起来第一件事就该报出 T21/T31/T50/T51 违反"每消费项有前置产出"。

**建议**：T50 拆成 T50a（宿主环境策略，假件逐维度，归 WP03）和 T50b（五家真实 spawn 逐维度，归 WP11b）；T21／T31／T51 整体移到 WP09b 或 WP11b。

同类但轻一些的还有两个：**T10**（"不同**实例**、**账号**、数据域出现相同原生 ID"）归 WP02（第 2 层），而实例在 WP09a（第 4 层）、账号在 WP09b（第 6 层）；**T55**（含"**第二宿主**"与双锁）也归 WP02，而宿主在 WP03（第 3 层）。这两个用合成数据大概能测，但测试文字得改窄，否则主责签不了字。

### 4.2 能力族和测试之间断了，最终对账没法机械执行

V1 的测试表有一列"对应能力"（T→C）。**V2 换成了 T→主责工作包，把 T→C 这一列删了。**

现在的映射关系是：

```
C → 主责WP     ✅ 41/41
T → 主责WP     ✅ 64/64
D → T          ✅ 12/12
C → T          ❌ 不存在
```

后果是 §13.2 第 1 条（"C01–C41 逐项保全，无隐藏退化"）和 WP13 的验收（"C01–C41 无孤儿能力；T01–T64 有主责和真实状态"）**没法机械核**：一个能力族可以一路走到 WP13 而**一条测试都没有**，没有任何检查会发现。

而且这不是假设。我按关键词全表扫了一遍（大小写不敏感，多种写法）：

- **C19（计划、步骤、子任务与子 Agent 活动）：64 个测试里一条都没有提到。** 它的主责是 WP06，而 WP06 只owns T28（Review 材料）和 T29（fork/compact）。
- **C03 的"未读"**：只有 T37 碰到"置顶、排序"，那是迁移前后对照，不是运行时行为。**"未读不能借原生 subagent 身份误归属"这条规矩，没有测试。**

C19 偏偏是最不能没测试的那个 —— 你 9-17 定的"改造后主控派活不是 Codex 的 sub-agent，底层是 CLI 派活给 CLI"就落在这里，C19 的正文也写了"原生子 Agent 不自动获得公共席位权限"。**规矩写了，没人验。**

**建议**：测试表加回 `对应能力` 一列，T61 的检查加一条"每个 C 至少有一个 T"。两分钟的事，堵的是最终对账的口子。

### 4.3 前六层是一根独木桥

跑了拓扑排序，实际并行度是这样的：

```
第0层  WP00
第1层  WP10a  WP01
第2层  WP02
第3层  WP03
第4层  WP09a
第5层  WP04
第6层  WP11a  WP05  WP07  WP09b     ← 到这里才有四路并行
第7层  WP08   WP06  WP10b
第8层  WP11b
第9层  WP12
第10层 WP13
```

**从 WP02 到 WP04 是四层纯串行，中间没有任何并行。** 这不是缺陷 —— 公共身份、数据根、宿主、探测、投递本来就有先后。但要认清后果：**在第 5 层跑完之前，你在界面上看不到任何变化。** V2 §8.3 的 S2 阶段（WP04/WP11a）才有"第一条受控完整链"。

它自己在 §8.3 说"布局、资源、工具和设置可并行" —— 那些都在第 6 层及以后，说的没错，但那已经是路走完一大半之后的事了。

**这一条不需要改计划，需要你知道。** 如果你希望早点看到东西，唯一能提前的是 WP10a（远程/语音封存，第 1 层）—— 那是唯一一个早期就有可见结果的包。

### 4.4 两处小的

- **WP00 名下零个测试**，但它的交付里写"T61 的计划依赖与责任检查先建立"，而 T61 的主责是 WP01。不冲突（"先建立"≠"主责"），但两处措辞对不齐。
- V2 §12 说"测试不能都拖到最后"，可分布上 **WP04 一个包扛 12 个测试、WP03 扛 9 个**，两个包占掉三分之一。这两个又正好是第 3 层和第 5 层的独木桥节点。集成热点和测试热点重合在同一个人身上，是排期风险。

## 五、要你定的两件

1. **AGPL-3.0-or-later。** `packages/seat-runtime/package.json` 写的是这个许可证。这些代码要进 gogoke 的桌面签名安装包 —— V2 §3.2 明说"本计划不作重新许可结论，也不将未解决来源问题的代码悄悄混入桌面包"。**这是你的代码、你的仓库，所以这大概率只是个换标注的动作，但得你点头。** 在这之前 WP03 的复用决定是悬着的。

2. **V2 §3.3 的跨语言方案。** 它提议：Rust daemon 是唯一权威，值得复用的 Claude/Grok TypeScript 协议代码通过一个**受限 worker** 接进来（worker 只做协议编解码和受控原生操作，不选实例、不持久化队列、不决定授权）。这是个真决定 —— 好处是不用把 1,676 行 Claude+Grok 协议代码重写成 Rust，代价是安装包里多一个 Node 运行时。V2 让 WP03 先做最小样本再定，这个顺序是对的。**你只要知道有这个岔路口。**
