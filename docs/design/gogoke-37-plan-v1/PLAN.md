## 1. 基线与授权顺序

- **映射快照**：写本计划时，读的是 main `d0e739be` 和 S1-R4 施工分支 `95b21a11`。施工分支还没有被接受，所以它只是一张快照，不是资产。
- **施工基线**是 R2-05 实际被接受的那次交付。开工前先做 **T00：在那个提交上重新核对**全部共享文件和资产。有任何变动，就修订本计划；MANIFEST 随之改变，之前的授权绑定也随之作废。
- **顺序**：
  1. 草案审查；
  2. T00 重新核对；
  3. 机器计划和 MANIFEST 定稿，合入 main；
  4. 另开一个单独的授权 PR；
  5. 合入后，按实际读回的内容核对授权；
  6. 第 0 步（L0）；
  7. 各线并行。
- **授权的形式**照搬 S1-R4，换一个独立路径：`artifacts/gogoke-37/intake/PUBLIC_AUTHORIZATION_RECEIPT.json`。授权里记录计划合入后，从 origin/main 读到的 `MANIFEST.json` 的 Git blob 编号。S1-R4 的授权不覆盖本计划，也不改动。**合并本计划，就等于 Owner 接受用这套授权方式来管设计 37。**
- **施工派活**依据 `AGENTS.md` 和 `docs/model-routing.md`。设计 37 里"主控自主编排"是产品规则，不能拿来授权施工派活。每条线派给谁，由施工控制席位按这两份文件定，计划只切线、不定人。

## 3. 第 0 步（L0）：共享接线和跨线约定

L0 由施工控制席位指定的**汇合席位**来做。它是 `PLAN.json` 里共享文件表（41 个文件）唯一的写入者。

- **共享文件表**：每个文件都写明给哪几条线开什么扩展点。范围包括：
  - native-host 的模块注册、IPC 分派、操作白名单、数据库初始化和迁移、可信签发边界；
  - Node 侧的契约、编解码、调宿主的客户端、服务组装、产品入口、适配器登记表和运行时目录；
  - Tauri 的命令注册、产品入口转发；
  - 界面的主框架和调用层；
  - 依赖清单、锁文件，以及三个 CI 工作流和服务端测试入口。
- L0 先把每条线要用的**最小扩展点**接通，这条线才开工。之后要再改共享文件，提交变更请求，写明是哪条线要改、影响哪份约定、通知了哪些线。
- **跨线约定一共 10 组**（K-SESSION、K-LEDGER、K-INBOX、K-QCARD、K-SIDE、K-SEAT、K-POLICY、K-INSTANCE、K-WORKTREE、K-UI）。每个操作都要定下：
  - 请求和回执；
  - 谁是可信的调用方；
  - 权限和版本检查；
  - 状态怎么迁移；
  - 重复调用、互相抢、断线恢复时怎么办；
  - 持久状态归谁。

  例子：收件箱消息带编号和修订号，编辑和取消按修订号竞争，没有回执不算送达；账本的实时订阅带游标和纪元，重复和缺口都有定义，每次读都检查读的人有没有这个作用域。
- **假实现和真实实现跑同一套约定测试。**假实现只用来让各线并行开发，任何验收项都不能在假实现上结算。
- **编解码兼容**：现有的编解码要求字段必须存在，也会拒绝不认识的版本。所以新增字段要走带版本的格式，并且证明旧记录还能读。

每条线只写自己的新目录（见 `PLAN.json`），共享文件一律不碰。

| **A 账本与上下文** | 统一成 ACP 事件，带作用域、席位、会话三个标签，另有旁聊层；重启对账；按作用域查询，实时订阅；渲染交接材料；会话用途和可读来源的规则（正式审查零继承靠这一条） | M1 |
| **B1 Codex** | 协议、续接、插话、只追加不回答、能力清单，按固定版本 | M1 |

## 5. 汇合点

- **M1 一个真席位**：L0、H、A、B1、C，加上 E、F 的第一阶段。一个 Codex 席位在自己的实例目录里跑通：开会话、收件箱、引导、问题卡、账本、停止事实、重启恢复。
- **M2 一个项目跑起来**：五家都接上，加 D，E、F 全部完成。跑通接手 → 在范围内编排 → 隔开写 → 合并 → 旁聊 → 规则原语，以及隔离测试。M2 里的"接手 → 派生 → 写 → 合并"只是一组可配置的验收场景，不是产品唯一的流程。
- **M3 候选**：加 G 和秘书长。从安装好的候选版本、通过真实界面走一遍，最后 Owner 在 Win11 上验收。

## 6. 验收

17 个验收项（V00–V16）。`PLAN.json` 里逐项写明：覆盖哪些需求、涉及哪几条线、在哪个汇合点用真实实现结算、要观察到什么。

- 设计 37 §13a 首版范围的九项、附录 A 的全部 25 个状态、以及几条固定规则，每一项都至少对上一个验收项。这一点由校验脚本检查。
- **模型自己说"没看到""没执行"，不算证据。**隔离类的验收用合成的标记，去看实际的输入记录、原生会话身份、宿主的拒绝记录和落盘记录。
- M3 要记录：确切的源码、安装包和 CLI 版本与哈希，云端运行和任务编号；执行、失败、跳过、没跑，分开记。

## 7. 构建与发布

照现行的[构建与发布治理](../../governance/gogoke-build-and-release.md)办，本计划不另立规矩：

- 原生代码和测试一律在云端跑；每个 CI 任务有超时；同一分支有新推送时，取消旧的运行。
- JS/TS 测试在本机只用签名的 Node 跑。
- 不以代码签名为前提，不改任何安全设置。一个组件或一个版本通过了，不外推到别的组件或版本。
- 现有的更新链，以及 Owner 离线签署的 `SHA256SUMS.windows`，保持不变。
- 证据公开之前，先用带正向样本的卫生检查扫一遍。
- **新的可执行组件**是五家 CLI，由 Owner 安装、宿主固定版本，要逐个记录它们在 Win11 智能应用控制下的实际情况。借来的 TS 零件放进服务包，不带原生插件。
