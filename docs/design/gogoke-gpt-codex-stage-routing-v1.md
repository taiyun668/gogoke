# gogoke：GPT / Codex 大阶段协作与施工团队适配规则 V1

2026-09-19｜工作流规则，不是生产开工指令，也不是已完成的逐文件施工计划。

## 1. Owner 规则与适用范围

GPT 负责需求澄清、研究、方案制定、架构取舍、完整施工计划、阶段复盘和下一阶段决策；Codex 负责执行已批准计划中的代码施工、集成、调试、测试和施工内独立代码复核。Owner 保留目标、范围、权限与最终验收权。

以可交付的大阶段移交，不以单函数、单任务卡、单 PR 或单工作包作为平台切换单位。连续施工仍有已定方案、依赖产物和明确授权时，继续在 Codex 执行；阶段结束后下一项工作属于研究、方案或非施工决策时，立即整理交接并回到 GPT，不在 Codex 开始新一轮方案研究。

本规则仅针对 gogoke Codex 去专属化项目。它作为原 V3 计划的平台分工补充：原文“Sol/high 定方案”“Controller 定目标”等，在本专项应解释为先由 GPT 完成研究和决策，Codex Controller 仅执行既定目标、范围内拆分与派发。模型角色名不等于平台；Codex 中调用更强模型也不能替代应该返回 GPT 的研究阶段。

不修改原技术范围、能力保全、WP 依赖、测试截止和独立审查要求；不改其它 held 工作包、Room 产品路由或运行时权限。涉及独立审计时仍遵守相应的上下文隔离规则，平台切换本身不证明独立性。

## 3. 施工团队适配，而不是把方案留给施工者

| 角色 / 既有路由 | 在本专项中的任务 | 边界 |
|---|---|---|
| GPT 方案责任方 | 完成研究、方案、合同、取舍、成套施工计划、风险预案、阶段决策 | 不能只给方向，让 Codex 补做总体方案；不冒充已完成生产实现 |
| Codex Controller：Sol/medium | 核实接包、排程、限定任务卡、工作区所有权、集成、施工内升级和回执 | 不另定产品目标、架构或安全合同；阶段研究转 GPT；模型身份须核实 |
| Luna/medium | 批准施工范围内的只读定位、依赖核对、日志收集 | 一般实现定位不是新研究阶段；若需要做技术选型或改变合同，提交 GPT 决策材料 |
| Luna/high | 简单、明确、机械可验的接线与施工 | 不顺手改 schema、依赖或权限 |
| construction：Luna/max | 边界完整的大批接线、夹具、长测试链 | 实际角色文件禁止自行 commit/push；由获授权的 Controller 集中集成与提交 |
| Sol/high | 已定界的复杂核心实现 | 负责实现批准的合同，不在施工中另定合同；实现者不能自我独立验收 |
| fresh Sol/high | 固定候选的独立代码复核、缺陷修复后聚焦复核 | 只读、独立，保留真实失败和未执行项；不是重新规划 |
| fresh Astra/xhigh | 高风险实现的首次 / 最终全轴审查 | 在批准测试与副作用边界内执行；不能只审部分轴就结束或改验收规则 |
| Astra/high Specialist | 对既定合同内的疑难实现提供定位材料 | 架构、安全策略、并发语义或矛盾证据需要研究裁决时，转 GPT，不用 Specialist 留在 Codex 偷做方案阶段 |
| Grok 独立通道 | 仅限当前能力和授权实际支持的独立任务 | 现路由记载只读、无终端/子进程能力；不列为必需施工工人或 acceptance auditor。能力和授权不足的整包改派 Luna/max 或 Sol/high |
| 外部 Claude | 保留最终异构审查义务 | 不宣称已经连接或自动派发；独立阶段评估由 GPT 统筹材料，Owner 最终裁决不变 |

固定角色不保证总能满足通用派发参数，任务卡必须与实际角色配置一致。研究和规划不再派给 Codex 的 planner 角色；已有角色文件不因这份文档被修改。

### 写入所有权与容量

一个共享文件在一个集成窗口内只有一个写入 / 合并所有者。`MainApp.tsx`、`types.ts`、`tauri.ts`、`lib.rs`、`state.rs` 和 daemon dispatcher 等热点须预先指定归属。并行只用于依赖可满足且写入范围不重叠的任务；没有可证明的独立边界时串行，不为利用模型而造任务。

仓库已读配置没有给出可据以固定的实时席位数或并发上限，本计划不虚构“同时 N 个工人”。GPT 给角色容量档和串行降级顺序；Codex Controller 在接包时报告实测可用槽位。容量不足先复用空闲角色或排队，不通过额外独立 Codex 会话绕过容量，不让 Owner 打开支线程逐个批准。worker 自测与独立验收分开，commit/push 与合并权限也分开。

## 4. 三个连续施工段的规划组织

下表用于把 16 个后续施工 WP 组织成大段，WP00/P00 已作为施工前基线单列。它不是新授权，也不是已经冻结的详细实施方案；原第 6 节全部依赖与第 9 节逐测试截止仍有效。

| 连续施工段 | 规划覆盖 | 阶段目标 |
|---|---|---|
| S1 底座与核心执行链 | WP10a、WP01、WP02、WP03、WP09a、WP04 | 保留式封存外部入口，建立公共合同、唯一 root/store/ExecutionHost、能力观察和安全投递链 |
| S2 产品贯通与能力矩阵 | WP11a、WP05、WP07、WP09b、WP08、WP06、WP10b、WP11b | 准入、屏幕与资源、设置、工具、上下文和重连贯通；形成跨提供方及 no-Codex 证据 |
| S3 迁移发行与旧接线退出 | WP12、WP13 | 在单独权限下完成迁移 / 安装 / 回滚验证、保能力退旧、最终全轴与异构审查 |

GPT 在每个大段前将该段关键合同和方案一次定清，并提前明确对下一段的接口；不能每完成一个 WP 才返回补一小段设计。各段内部仍按依赖分批集成、独立复核，不取消必要检查。

授权范围可小于规划范围。D 目前只建议首批 WP10a/WP01，尚无实际生产授权；S1 中其余 WP 不因在同一行就获权。GPT 应事先准备整段依赖、边界与预案，Owner 可明确整体或分批授权；授权确认不必重做方案。连续的下一段若计划、产物与授权均已具备，也不强制为了平台轮换先回 GPT。

WP11a 的真实账号 / 原生调用、WP12 的真实迁移 / 安装 / 发布等另需明确授权。未授权部分保留为待办，不借“连续施工”自动执行。

## 5. GPT 交给 Codex 的必须是成套施工包

每个阶段施工包至少包含：固定源码与证据 SHA、目标 / 非目标、允许文件、合同与错误语义、任务及依赖图、团队角色与写入所有权、串并行规则、测试命令和预期行为、独立审查安排、回滚与资产保全、停止条件，以及完成后的去向。

高影响问题必须在 GPT 侧明确到可以执行：公共 schema、owner/root/writer、权限、进程身份与停止、迁移、原生 / 公共边界。尚未决策的阻断项不能写成“施工时研究”，也不能靠填未知字段标 READY。非阻断未知必须绑定具体责任、验证期限和禁止假设。

同一段包含批量任务卡。Codex 可以按预定依赖和容量细化步骤、选择合同内等价实现、调整派工顺序；不得越过已冻结的行为、权限、范围和验收标准。小步提交是施工手段，不等于小步平台切换。

使用配套 `gogoke-construction-stage-pack-template-v1.md` 编制下一份实际施工包。模板不是已经完成的施工包；未填完关键字段或未获明确授权不得开工。

## 6. 哪些问题留在 Codex，哪些必须回 GPT

| 情况 | 处理 |
|---|---|
| 普通编译 / 类型 / lint 失败，已定接口下的接线、测试或回归缺陷 | Codex 内定位、修复、重跑、独立复核，不单独切 GPT |
| 测试暴露实现偏离已批准合同，修复不改合同 | Codex 集中修复同批问题并复核，不把每个 bug 变成研究课题 |
| 同一失败连续两次 | 返回 Codex Controller 诊断和重派；若仍属既定实现范围不自动打扰 Owner 或切平台；一旦需要新方案则转 GPT |
| 当前阶段结束，下一步是研究 / 方案 / 独立阶段性决策 | 先固定必要状态与交接包，随即转 GPT；不自行在 Codex 继续研究 |
| 必须改变目标、公共合同、schema、owner/root/writer、安全 / 并发 / 迁移语义、采用范围或验收标准 | 立即停止受影响路径，整理事实与待决问题交 GPT；不为凑批次继续危险操作 |
| 下一项仍属已有方案与授权覆盖的连续施工 | 继续 Codex，包括跨 WP / PR / 内部里程碑的执行 |

非阻断疑问集中入决策账本，在自然阶段边界批量交 GPT；真正改变安全、数据或架构边界的阻断立即移交。只可继续不依赖该决策、仍获授权且不会污染证据的并行工作，不能以“不切细”为理由压住重大问题，也不能整仓无故停工。

施工内代码审查、集成回归和批准的有效 mutation 属于施工质量控制，可在 Codex 完成。其结论若引出新的方案取舍或阶段研究，后者必须在 GPT 完成。保留 fresh 审查、全轴风险检查及最终异构审查，不把不频繁切换解释为删除审计。

## 7. 阶段交接与连续推进

Codex 阶段结束时固定实际提交 / 分支、代码差异、完成与未完成矩阵、真实命令 / 退出码 / 失败日志、独立复核、未执行轴、资产保全 / 回滚、剩余决策和推荐下一步。沿用原 Task Capsule 回执字段，增加：`PHASE_ID`、`PLAN_COMMIT`、`AUTHORIZATION_REF`、`NEXT_WORK_KIND`、`NEXT_PLATFORM`、`DECISIONS_REQUIRED`。

`NEXT_WORK_KIND=IMPLEMENTATION` 只有在计划、依赖与授权都满足时才可继续 Codex；为 RESEARCH / DESIGN / PHASE_DECISION 时转 GPT。GPT 基于固定交付做复盘与方案，不从聊天摘要假定代码状态，也不把旧审查当作新 SHA 通过。

“第一时间转向 GPT”是任务与责任切换要求，不表示现有工具能自动创建、发送或切换另一平台会话。可执行交接应提供固定入口与整段任务，由实际可用且已授权的通道移交；不让 Owner 反复搬运每个子任务或 worker 回执。
