## Decision and implementation boundary

Recommend the **whole authoritative store in Rust native-host**. The same native-host that owns root identity and the root lock owns the only product SQLite connection, compiled SQLite, VFS, transaction executor, persistence validation, projection writes, migration ledger and query implementation. It remains a subordinate persistence/OS component of the one T3-derived service. Node retains command admission, the T3 command queue, pure decider, in-memory read projection, provider parsers/reactors and authorized dispatch policy. Rust does not independently schedule or choose product work.

Node submits one finite typed operation, not SQL or a connection/path. Rust validates it, derives the complete write set and commits it on one connection. Product database files, including read-only preflight, are never independently opened by Node. Native workers receive neither database paths as capabilities nor inherited database/root handles.

| Shape | Concrete atomicity mechanism | Consequence |
|---|---|---|
| Rust owns file/VFS; SQLite remains inside Node | A reviewed native addon would have to replace `node:sqlite`, own a single SQLite handle created by the Rust VFS, and execute the entire event/projection/receipt callback through that same handle. Effect's transaction context must keep every repository statement on that connection; nested projector transactions must remain subordinate savepoints, with only the outer commit visible. One compiled SQLite image must contain both the VFS and database engine. | Stock `DatabaseSync(filename)` cannot consume the pinned handle. A generic SqlClient adapter still exposes arbitrary SQL to Node and lets it split required writes; wrapping its calls in IPC does not satisfy Owner's restricted-interface condition. Constraining that addon to complete typed operations requires the same persistence boundary redesign and adds Node ABI/FFI lifecycle work. Not selected. |
| Entire authoritative store in Rust; Node calls typed operations | A single `CommitOrchestration` request executes `BEGIN IMMEDIATE`, authority/precondition recheck, intent/object writes, all donor events and derived projections/cursors, required R4 records, accepted command receipt, then one `COMMIT`. Any pre-commit failure rolls back the entire set. Rust generates projections from the admitted event variants; Node cannot omit individual projector writes. | Selected. Existing T3 `withTransaction` is replaced at the orchestration seam, with differential tests against its current behavior. No transaction can span multiple independent RPC calls or connections. |

The rejected option is not a statement that an addon is impossible. It is a comparison of the work required to preserve both the fixed atomicity and the newly explicit restricted interface. There is no supported stock-Node handle-adoption shortcut in the inspected adapter.

## Native file and SQLite lifecycle

Implement in the standalone `apps/desktop/native-host` boundary; `crates/**` and P05 historical evidence remain read-only. Preserve `RootIdentity`, alias/case/junction normalization, explicit `rootId` binding, non-inheritance and the root-lock lifetime. Never fall back to cwd or a fresh empty database after an error.

The main database open becomes a private VFS-owned `VerifiedDatabaseConnection<'root>`: one native `CreateFileW` for main DB with data I/O plus required identity/access rights and omitted share-delete, immediate same-handle identity/type/root verification, then SQLite pager access using that handle. Do not acquire the old DELETE pin and ask stock SQLite for a second path-open; do not drop the strong pin to make a second open work. Refactor the pin's strong ownership into the VFS connection without exposing raw handles. The exact adopted access/close implementation needs Windows conformance against the retained contracts. Creation uses CREATE_NEW only for a proven new fixture root; an existing file path cannot truncate or create as a recovery action.

Audit all Windows VFS entry points, including `winOpen`, main-file reopen/fallback branches, shared-memory mapping, WAL/journal/temp opens, access/delete callbacks, URI options, `ATTACH`, extension entry points and automatic initialization. Main identity verification must precede SQLite header read, PRAGMA, schema access, migration and automatic extension callbacks. Rejected/ambiguous opens must not retry through the stock VFS. WAL/SHM are separate objects with their own bounded root/name/identity checks; the main-file pin proves nothing about their identity. An implementation that merely changes main `shareMode` is insufficient.

Only admitted built-in initialization may run; loadable/process-global extension registration is inaccessible to product callers. Native build provenance records compile options and source/patch hashes. No ambient library lookup may silently link a different SQLite. Check every connection's foreign keys, WAL and synchronous FULL before product writes. This is a durability configuration claim, not a hardware power-loss claim.

The root lock lives through transaction drain, explicit database/statement/sidecar shutdown and custody recording. Close ambiguity is `UNKNOWN`; Drop is not success evidence. A crashed process may release OS handles, but the next process cannot infer that durable launch/action custody is settled merely because it acquired the root lock.

## Restricted interface and transaction semantics

The operation catalog in `artifacts/s1-r4/tasks/R4-SQLITE-ROUTE-B/interface-shape.json` is scaffolding for a reviewed protocol, not a runtime schema or another authority ledger. Bind requests to the existing private current-user IPC session, principal, root/domain, host epoch and binding generation. Carry counters as canonical decimal strings and canonical bytes as bytes with hashes recomputed by Rust. Reject duplicate keys, overflow, unknown protocol/operation variants and caller-supplied authority claims.

`CommitOrchestration` takes command/operation identity, canonical admitted intent, expected snapshot/stream revisions, typed event proposals and bounded R4 object links. It has no SQL, table names, arbitrary predicates, migration script, database filename, `BEGIN`, `COMMIT`, savepoint or raw receipt-upsert field. The Node decider remains the service's decision implementation; proposals carry no privilege by themselves. Rust validates against the existing contract/rule version, current stored authorization, domain/principal/generation and allowed command/event relationship. It allocates durable sequences and derives the required projection and receipt facts.

Inside one immediate transaction:

1. Recheck access and epoch/generation before even returning an idempotent result. Resolve `(domainId, operationId)` against canonical request fingerprint. Same ID/different payload, target or generation is conflict; a matching existing receipt reconciles without repeating effects.
2. Recheck all snapshot/stream preconditions used by the decider. Stale decisions return a typed conflict, not partially applied writes. Preserve the donor's auto-settle/recreation protections and expected read state.
3. Write the canonical intent/object and native identity bindings; append every donor event with its stream version, actor/origin/causation metadata and sequence; derive all affected projectors and advance their cursors; write any required R4 event/object/receipt records in this same transaction. A linked R4 record and donor orchestration operation cannot call two independently committing methods.
4. Derive accepted command receipt from the actual final appended event/sequence. There is no public arbitrary `upsertReceipt`. Verify complete required write-set invariants, then commit once.
5. Return exact committed events, receipt and snapshot revision only after the commit result is established. Update Node's in-memory model, publish events and run existing deferred attachment cleanup only after this return. No provider invocation, pipe activation or arbitrary Node callback occurs while a database transaction is held.

`CommitDomainRecord` preserves the current core object/event/receipt operation for operations with no donor orchestration action. `CommitOrchestration` invokes that internal implementation in the same transaction when linkage is required; no nested independent commit. Future Decision/resource/action batches are additional closed typed variants with their fixed complete write sets, not a generic write-batch escape hatch.

`RecordRejectedCommand` persists an actual rejection plus the required intent/error evidence with no fabricated accepted event. Preserve donor's accepted/rejected distinctions. `ReconcileOperation` reads original identity/fingerprint and authorization, returning committed, definitively not committed, conflict, or unknown. Transport loss or COMMIT error produces `COMMIT_UNKNOWN`; do not blind retry or translate EOF/exit-zero into acceptance. Queries (`ReadEvents`, `ReadAggregateRange`, `ReadSnapshot`, `GetReceipt`) use closed parameter/result shapes, bounded pages, snapshot/domain cursors and a consistent read transaction. Writes for provider runtime/custody or metadata are individually named typed operations with admission checks; there is no generic key/value or arbitrary patch endpoint.

## Schema, migration and data boundary

Use only new-version scratch roots in this stage. No user Home, donor user database, legacy store, credentials or native runtime history is imported. Native preflight verifies the owned actual file/header/integrity and fixed schema/migration identity before mutation. Unknown newer schema, malformed migration ledger, corruption or failed migration preserves the original and rejects start. No empty-store fallback.

The donor already has data-transforming migrations (for example `026_CanonicalizeModelSelectionOptions.ts` rewrites event JSON as well as projections). Preserve its fixed fixture transformation semantics rather than assume all 53 are static DDL. Build a per-migration manifest from the fixed source and test every ordered prefix/target with the existing migration tests. Do not modify published donor migration text or infer runtime authority from `CREATE TABLE IF NOT EXISTS`.

A fixture migration runs under native root/file custody with migration ledger and DDL/data changes in the same connection transaction. Preflight validation occurs before writable mutation. Failure must preserve the original supported fixture state; test backup/export only on experimental copies. Future context/decision/evaluation/dream migrations remain versioned and mapped to their existing DAG tasks; they execute through native-owned fixed migration code, never Node-supplied SQL. Importing old P05 schema or its `crates/gogo-store` implementation is outside this recommendation.

## Equivalence and falsifiable validation

The donor is the oracle for preserved behavior, not for R4 additions. Use identical deterministic commands/event IDs/times and initial fixture schemas. Run the original donor against its own disposable SQLite file and route B against a different disposable root. Compare normalized typed results *and actual stored rows*, event bytes/order/stream versions, receipts, projection states, restart snapshots and error classes. Oracle process never opens route-B files. Existing R4 independent field rules and canonical-byte fixtures remain the oracle for R4 additions.

Required first slice: one project creation followed by a thread/message sequence, a duplicate command, a same-ID changed payload, and a projector rejection. Assert intent + event(s) + all applicable projection/cursor writes + receipt appear together, or none do. Run failures after intent, each event, each projector/cursor, receipt, immediately before commit and immediately after durable commit before reply. A projector write failure must leave no accepted receipt or event. A lost reply must reconcile exactly once without re-dispatch. Multi-event command failure cannot leave a prefix.

Further mandatory axes: competing processes with root aliases/case/junction; existing-file corruption and unknown schema; migration failure and prefix fixtures; actual Windows rename/delete/replacement attempts while SQLite reads/writes/checkpoints; WAL/SHM collision/reparse and crash preservation; external DELETE/share conflict in both acquisition orders; extension-before-proof attack; cross-domain/principal/epoch request rejection; revoked-access idempotency read; stale decider revisions; borrowed handle close/Drop errors; stop/drain with pending operation; consistent read pagination during writes; safe integer boundaries; replay cursor and deferred cleanup failure/restart; denied direct database open in the built Node product graph.

Instrument runtime build identity (native binary, SQLite source and patch, compile options, protocol/schema fingerprints, plan/auth/candidate and loaded Node module graph). Build-graph closure plus a runtime native-open sentinel is required for the no-Node-open invariant; `rg` alone cannot prove it. Check C compilation/syntax under deliberate behavior mutations before using red tests as evidence.
