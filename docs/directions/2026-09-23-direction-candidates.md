# gogoke 方向候选（2026-09-23）

- 来源：Owner 与 Claude（审计席）的侧边讨论，以及对已停项目 NaveHQ 目标蓝图 v1.0 的回读
- 状态：**候选，不是决定**。不改变 S1-R4 计划 v2、授权或施工规则，不派施工。
- 时机：按 Owner 意见，S1-R4 闭环在 Owner 机器上跑通之后再逐项评估；现在上马会把协调压力全压回 Owner。
- 采用方式：Owner 选定后交主控，按计划规则进入后续计划修订。

## 1. 反射神经：Jev 与判断闭环

Jev 在设计中是主控的判断后端（DecisionProvider），相当于 gogoke 的**反射神经**：Owner 是大脑，日常判断练熟一类，就变成反射直接处理，只有真正需要大脑的事才上报。结构上是"AI 化的 if"：分支由代码列出并先滤掉不合规的，Jev 在合法分支里选，永远保留等待 / 都不选的出口。

Owner 的意见（本次讨论中明确）：

- **分阶段放权**：数据不足、置信不够时只做分拣和提示；某一类判断积累到足够数据、校准证明够准后，成为直接决策节点。按判断类别分别放权，不整体放权。
- **换版本不作废数据**：判断与结果记录在我们自己的库里，校准和反馈是持续的；换版本作废的只是旧版本的"自动采纳资格"，用回放把历史记录重问一遍新版本即可快速重新校准。回放中新版本选了当年未执行的候选时，没有结果可对照，这部分需上线后再积累。
- 这个闭环形状上等同后训练（判断 → 下游打分 → 反馈 → 下一次更好），区别是不改 Jev 权重，改的是信它多少、怎么问它、什么时候不问它。

不随置信度变化的边界：不扩大权限，不取消必需复核，不给自己的判断打分（否则校准数据失真）。

判断位置可插拔，下列都是可接进同一位置、吃同一份判断与结果记录的候选：

- 上下文老虎机（如 Vowpal Wabbit）：好量化的资源选择，本地、不外发。
- 用自有记录训练的本地小模型：真正意义上的后训练，数据够的类别接手。
- 先例检索：按最相似的历史判断及其结果来判，可解释，记录一多即可用。
- 把 Owner 的高频纠正提炼成规则，经 Owner 确认后进 Git。
- 自动优化提问（如 DSPy）：对应 Dream 的"优化怎么问 Jev"。

接 Jev 前，用同一批历史记录回放，与规则、其他模型对比，数据证明更准再让它坐这个位置。

设计 18 个场景之外的候选判断：

| 场景 | 可长到 |
| --- | --- |
| 会话在推进还是在空转；空转后换人还是重开 | 直接决策 |
| 侧边聊天结论分拣：计划已有 / 与现行冲突 / 需 Owner 拍板的新决定 | 直接决策（新决定仍递 Owner） |
| 计划项是否为本轮目标所必需（防"往满了做"） | 直接决策 |
| 收件箱条目分拣：仍存在 / 已修复 / 已取代，是否需要报 Owner | 直接决策 |
| 规则有没有 Owner 决定来源 | 只到提示（来源就是 Owner 的决定） |
| 回执与证据是否对得上 | 只到提示（真假由代码核） |

## 2. 整体能力：可引入的现成器官

- **Agent Client Protocol（ACP）**：统一驱动各家编码 agent 的开放协议。若可用，接新 agent 从施工变成配置。须先按 §5 的一票否决条件验证。
- **时间知识图谱式项目记忆**（如 Graphiti、Mem0）：记录每个决定的时间、来源、理由、是否被推翻。底子仍是 Git，只做可查询"为什么"的索引。
- **产物出处证明**（如 GitHub 构建出处证明）：安装包附带"哪次提交、哪次云端构建"的可验证记录。不是代码签名，不改变现行不签名的更新链；是否采用由 Owner 定。
- **全链路追踪**（如 OpenTelemetry）：每个 agent 在做什么、耗时与花费、卡在哪里，是判断空转的感官。
- **云端沙箱开发环境**：工人在云端隔离环境编译测试，本机 Smart App Control 与磁盘不再约束施工和并行。
- **gogoke 自身的评测基准**：录下真实项目当考题，每次改 gogoke 重放，量派活是否更准、Owner 介入是否更少。

不采用：基于图的编码代理（代码图谱）。它是工人读代码的能力，不属于 gogoke 这一层（章程 §4.3 不替代 IDE 与模型供应商）。仓库到几十万行级、出现漏改远处调用方或读代码耗费占主导时，可在工人一侧挂接，不改 gogoke。

## 3. 分布式：重点是活怎么切

gogoke 已经半分布式：账本在 Git/GitHub，网页端 GPT、本机 Claude、云端 CI 通过 PR、施工分支和收件箱协作。仍是单机的是活跃协调（认领、租约、托管、派发）。

方向：一个大脑、很多双手。协调者只留一个，不做多主；工人分散在任何地方，按租约领活；远期可把协调者从 Owner 个人电脑移到常开节点。

真正的难点是切活：

- 按写入范围切，不按功能切；
- 先冻结接口，再对着接口与假实现并行；
- 每一块有自己的验收；
- 切的代价是上下文交接，复核能力也是瓶颈，不是越细越好。

现状诊断：v2 五个包是 R2-01 → R2-05 的直链，未标写入范围，只能单线施工，其他模型只能分到复核。其中 R2-04（云端随包与受管启动）在先冻结宿主启动接口后，可与 R2-02 并行。根治方式是方案阶段就产出切分图：可同时开工的线、各自写入范围、冻结的接口、各自验收、汇合点。

## 4. 其他方向

- **Owner 决定登记册**：Owner 的每个决定作为一等对象进 Git（来源、日期、适用范围），新方案和新规则出来时自动对照，冲突先拦。近期返工多数来自方案丢失或违背已做决定（账本分工、构建约束、签名）。可先以文档起步。
- **先自动化 Owner 现在手工做的事**：转话、复制提示词、贴回执、点合并、询问进度。以"能否少掉 Owner 一次手工动作"排优先级。
- **订阅额度作为调度资源**：Owner 已确认这个方向。调度器知道每个账号剩余额度与恢复时间，把活派到有额度的地方。须同时考虑 §5 的计费线。

## 5. 从 NaveHQ 回读的候选

以下来自 NaveHQ 目标蓝图 v1.0，gogoke 目前没有对应物：

- **段落价值对账**：每段报"离目标多近"，不报"完成多少"。成立须三样齐全：独立拉取的 git 真相、开工前锁定且不可事后修改的通过题、非派活方的缺口判断；缺一即不得向 Owner 报进度。用于识别"产出很多、没靠近目标"的高级空转。
- **失败分诊**：失败后先判根因。粒度错回去重切，匹配错换更合适的重派，反复无进展举手找 Owner。二者搞反即双输。
- **方案输出包**：规划阶段须产出依赖与并行图，以及 **Owner 触点预算**（预计 Owner 出面几次、每次原因、为何只有 Owner 能判断）；不必要的 Owner 往返视为计划缺陷。
- **雷达、坑库、轮子库，接入 / 借鉴 / 自研三档**：遇新能力先扫现成方案；可依赖则接入，不可依赖则只借思路自己实现，都没有才自研。
- **组队模式**：solo、pair（一写一审）、panel（多方出方案 Owner 选）、red-blue（一方设计一方攻击）、pipeline（上下游接力）。
- **计费线**：手动交互运行走会员订阅额度；无人值守 headless 自动运行一般需 API Key 计费。额度调度与全自动化须把这条线算进去。
- **编排引擎一票否决条件**：必须非侵入（驱动现成 CLI，保留原生登录与会员额度路径），必须可交互接管。按此标准，Temporal 这类把 CLI 降为一次性调用的引擎不适用。ACP 等候选须按这两条验证。
- **坑：AI 自写规则文件有害**。NaveHQ 坑库记录的研究结论：agent 自写的规则文件降低成功率、抬高成本。规则由 Owner 给方向、人来定，与"Owner 决定登记册"方向一致。

## 6. 建议的评估顺序

S1-R4 跑通后，建议先评估段落价值对账与方案输出包（并行图 + Owner 触点预算）：前者防空转，后者防把协调压力压回 Owner。其余按 Owner 选定。
