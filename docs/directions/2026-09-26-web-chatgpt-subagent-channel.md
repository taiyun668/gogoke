# 网页 ChatGPT 子 agent 通道：需求

- 日期：2026-09-26
- 来源：Owner 与 Claude（审计席）的讨论。经三轮修正定稿，Owner 已确认"好的"。
- 状态：**需求，尚未施工。**试跑结论出来后，再通过 PR 修改 [model-routing.md](../model-routing.md)（按规则由 Owner 合并）。
- 一句话：Codex 需要子 agent 时，如果这件活划算转出去，就用一个 skill 在内置浏览器里把它交给网页 ChatGPT，交接全部在 GitHub 上完成；网页端的每个档位按天、按周限量计数，不划算的活仍由主控直办或交给 Codex 子 agent。

---

## 1. 为什么做

- 网页 Chat 的额度和 Codex、ChatGPT Work 的额度**分开计算**（官方帮助中心原文），等于多出一个额度池。
- **GPT-6 Pro 就是 GPT-6 Astra**（原文 "GPT-6 Pro, powered by GPT-6 Astra"）。把现在由 Astra 子 agent 做的活转过去，模型不变，只是换一个额度池。
- gogoke 的施工本来就在 GitHub 上：云端 CI、分支、PR、检查点。网页 ChatGPT 通过 GitHub 连接器能读也能写，历史上已经承担过整段施工。

## 2. 事实：可用档位与额度

来源：[GPT-5.6 and GPT-6 Pro in ChatGPT](https://help.openai.com/en/articles/20001354-gpt-56-and-gpt-6-pro-in-chatgpt)，2026-09-26 读取原文。

| 档位 | 模型 | Pro $200 档的额度（仅限 Chat） |
|---|---|---|
| GPT-6 Pro | GPT-6 Astra | 每周 200 条 |
| GPT-5.6 Sol Pro | GPT-5.6 Sol Pro | 另算每天 170 条；与 GPT-6 Pro **合计每天不超过 200 条** |
| Extra High / High / Medium | GPT-5.6 Sol | 官方未公布具体数字，只说"取决于套餐" |

- GPT-6 只有 Pro 一个档位，其余档位都是 GPT-5.6。
- **GPT-6 Pro 的周额度用完后，会自动切换到 GPT-5.6 Thinking Medium**，不会拦截。GPT-5.6 各思考档用完后，也"可能换用另一个可用模型"继续。
- 网页上**看不到剩余额度**，只会在能给出的时候显示重置时间。
- 按使用条款，平台对滥用可能施加临时限制。

## 3. 派活的经济账：主控直办 / Codex 子 agent / 网页 GPT

| | 主控直办 | Codex 子 agent | 网页 GPT |
|---|---|---|---|
| 消耗的额度 | Codex（主控） | Codex（Astra 最贵） | 网页 Chat（另一个池） |
| 交接成本 | 零，上下文就在手上 | 写任务说明；可以继承上下文 | 任务说明必须先提交到 GitHub；不能继承上下文 |
| 等待时间 | 最短 | 短 | 长，Pro 常需要十几分钟 |
| 能否碰本机 | 能 | 能 | 不能 |
| 额外开销 | 无 | 起一个子会话 | 主控要准备、派发、取回结果，这部分也消耗 Codex token |

**转给网页 GPT 必须同时满足五条：**
1. 任务能独立成包：零继承，或者一个交接包就够；
2. 分量足够大：换成 Astra 做会明显消耗 Codex 额度（长篇审计、大块施工、深度排查）；
3. 不在急路径上：等十几分钟不会卡住主控的下一步；
4. 不需要碰本机；
5. 结果能在 GitHub 上验证：一次 CI 运行，或一份带提交号的结论。

**以下情况不转：**
- 小活、快速核对：主控直办，派活开销会高于省下的额度；
- 需要继承主控上下文的调用，例如 `fork_turns all`：留在 Codex；
- 在急路径上、需要频繁来回的修复：交给 Codex 子 agent；
- 必须在本机做的四类：正式签名、Win11 智能应用控制下的实测、真实 CLI 联调、本机工作区杂务（清理、读本机日志等）。

## 4. 每日限额与用法

- **每个档位都设每日上限**，周额度要摊到每一天，不能一天用光。以下默认值 Owner 已于 2026-09-26 确认：
  - GPT-6 Pro：每天最多 25 条（一周约 175 条，留出余量，也留给网页施工席位）；
  - GPT-5.6 Sol Pro：每天最多 120 条（Owner 2026-09-26 要求放大；官方上限为每天 170 条，且与 GPT-6 Pro 合计不超过每天 200 条。25 + 120 = 145，余下的 55 条留给网页施工席位和临时需要）；
  - Extra High / High / Medium：先给一个保守的每日数，再根据试跑中实际撞到的额度调整（见 §5）。
- **每个档位接什么活：**
  - GPT-6 Pro：只接重活，例如冻结候选前的全面审计、复杂设计、疑难排查；
  - GPT-5.6 Sol Pro / Extra High：常规审计、中等规模施工；
  - High / Medium：窄修、复核；
  - 小活不进 Pro。
- 每个任务设追问上限；同一个问题连续失败就停下交还主控，不重复派发。

## 5. 计数器

- **完全自己记账**：每个档位按天、按周累计，按官方重置规则清零。
- **网页施工席位的用量合并计入**：它和子 agent 共用同一组额度。
- **每次发送后核对实际回复的模型。**一旦发现被自动切换（例如 6 Pro 用完被换成 5.6 Medium），就把该档位记为用完，并记下时间点和页面显示的重置时间，暂停使用这个档位直到重置。这同时用来校正自己的计数，也用来学出未公布档位的实际上限。
- 计数器和额度表的当前状态，主控和 Owner 随时可查。

## 6. 调用与交接

- 做成 Codex 的一个 skill，**只用 Codex 内置浏览器**：不开隧道，不做系统桌面操作，不和 Owner 抢屏幕。
- 每个任务**新开一个对话**，不进带记忆的 Project；审计必须是干净会话。
- **派活前：**先把任务说明提交到 GitHub。启动词只写：任务编号、角色、仓库、分支、基准提交号、说明文件路径、允许写入的分支与路径、结果写到哪里、停止条件。
- **发送前：**核对页面上选中的模型和档位与计划一致，不一致就不发。
- **交接只走 GitHub**，Codex 只到 GitHub 取结果，不读网页：
  - 审计：结论写到固定位置（收件箱分支上的固定文件，或 PR 评论），必须带所审的提交号；
  - 施工：推到专属分支，并带检查点。
- **权限边界：**只推送到分配给它的分支；不合并 main、不发布、不接触密钥和签名。
- **验收：**与其他施工席位相同——必须有真实的 GitHub Actions 运行，执行数大于 0，并在合并前复核。它自己说"已完成"不算。
- **兜底：**超时、网页故障、额度不足或模型不对时，自动降档或退回 Codex 子 agent，并记下原因。网页端不能是唯一通道。

## 7. 记账与回看

- **派活时：**估算三条路各自的花费，记下选了哪条、理由是什么。
- **完成后：**记下实际花费——Codex 端 token、网页端条数与档位、等待时长、是否返工、是否降档或退回。
- 对话链接只保存在本机，不进公开仓库。
- **定期回看：**哪些类型的活转过去真正省了、哪些不划算，据此调整 §3 的条件和 §4 的限额。条件和限额由数据校准，不一次定死。

## 8. Owner 触点

| 触点 | 次数 | 为什么只能 Owner 做 |
|---|---|---|
| 在 Codex 内置浏览器里登录 ChatGPT | 一次 | 账号凭证 |
| 确认 §4 的默认限额与档位用法 | 一次 | 额度是 Owner 的资源 |
| 拍板启用 | 一次 | 方向决定 |
| 每个任务 | 零 | — |

## 9. 试跑要核实的

- **试跑的安排（Owner 2026-09-26）：**
  - 另开一条 Codex 线程开发并试跑这个 skill，不打断主控线程正在做的施工包；
  - skill 完善后，再交给主控线程采用；
  - **试跑期间禁止使用 GPT-6 Pro**，只用 GPT-5.6 的各档位；
  - 试跑任务从不影响当前施工包的低风险活里挑。

- 网页 GPT 能否通过连接器读到 Actions 的运行结果和日志；读不到的话，由 Codex 把结果摘要提交给它。
- 各档位的回复时长，用来确定超时。
- 内置浏览器的登录能保持多久。
- 使用条款中关于自动操作网页端的规定，在正式启用前核实。
- 未公布档位的实际上限，按 §5 学出来。

## 10. 不做

- 不用"隧道 + 桌面 Computer Use"那类方案（例如 codex-with-chatgpt）。
- 不把网页端当唯一通道。
- 不追求"能转尽转"：每一次都按 §3 的经济账决定。
