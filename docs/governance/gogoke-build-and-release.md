> **这是一份长期治理文档，不属于任何一个施工阶段。**

## 一句话

**Owner 的这台 Windows 开着强制模式的"智能应用控制"，它会拦截本机新编译出来的未签名程序。所以 gogoke 的原生代码一律在 GitHub 云端编译；发布不买代码签名证书，而是用 Owner 离线签名的校验清单保证完整性（Sandglass 的做法）。**

这不是偏好，是这台机器逼出来的。忘了这一条，施工就会在本机撞墙——2026-09-22 已经撞过一次（见第九节）。

## 一、这台机器的约束

**智能应用控制（Smart App Control）处于强制模式。**

```
注册表  HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy
        VerifiedAndReputablePolicyState = 1          （0 关 / 1 强制 / 2 评估）
策略    VerifiedAndReputableDesktop
        {0283ac0f-fff1-49ae-ada1-8a933130cad6}
拦截    Win32 错误 4551；Code Integrity 事件 3077（拦截）/ 3033（签名级别不达标）
日志    Microsoft-Windows-CodeIntegrity/Operational
```

关于它，已经被实测确认的事实——**每一条都有出处，不要凭印象推翻**：

1. **它不支持任何例外。** 不能按程序、按文件、按目录放行。只有开和关。（Sandglass README）
2. **它拦的是"未签名、它拿不准"的程序，而且逐个文件判断。** 2026-09-15 本机编译 CodexMonitor 时生成 54 个构建脚本，**只拦了 1 个**；同样未签名的 Flutter 样品从没被拦。（当日日志）
3. **拦不拦的原因不可解释。** Sandglass 记录过：**同一份字节隔约 18 小时从被拦变成放行**，原因至今不明。Sandglass 的规矩是："**不写成信誉或时间效应**"，每个新版本都是新哈希，**过去的放行记录不保证下一版**。（Sandglass `docs/handoff-2026-09-02.md`、`docs/release-checklist.md`）
4. **主程序能跑，不代表它启动的子进程能跑。** Sandglass 实测过已安装程序的子进程被单独拦截。（Sandglass `docs/release-checklist.md` 第 902 行附近）
5. **SignPath 提供的 OV 证书签名，已验证能通过它。**（Sandglass `docs/handoff-2026-09-02.md`）
6. **不要为了开发、测试或安装去关掉它。**（Sandglass README；Owner 一贯规矩）

## 二、为什么以前的 GOGO 房间从没被拦

房间一直用 Node.js 跑。真正运行的是**有正规签名的 `node.exe`**，我们写的只是交给它执行的脚本，**从头到尾没有在本机编译出新的程序文件**。

智能应用控制拦的是"新编译出来的未签名程序"，所以房间碰不到它。此前唯一一次撞上，是编译 Rust 内核（`crates/`）跑测试时报的 `os error 4551`——同一个机制。

**记住这个区分，后面所有决定都建立在它上面：**

| 运行方式 | 会不会被拦 |
|---|---|
| 签名的运行时（`node.exe`、`python.exe`）执行脚本 | 不会 |
| **本机新编译**出来的 exe、dll（Rust 构建脚本、过程宏、测试程序） | **会，而且不可预测** |
| **云端编译**、装到本机的程序 | 截至 2026-09-22，gogoke 安装目录 0 次被拦（但见第一节第 3、4 条，**不可外推**） |

## 三、2026-09-15：一天之内怎么走到现在的架构

### 08:41　选 CodexMonitor 当壳

Owner 此前连续两天自己做 UI 做不出来，决定接一个现成的、"看着就对"的界面当底座，而不是让 agent 去猜长相。

CodexMonitor 满足全部条件：**MIT 许可**可以随便改；**支持 Windows**，Owner 本机已装过它的 0.7.67；Owner 本机有一份带中文界面的源码。它是 **Tauri + React**：前端约 7.5 万行 React，后台约 2.8 万行 Rust。

Owner 同时定了：**功能一个不砍，只做适配。**

### 08:59　本机编译 Tauri，撞上智能应用控制

Tauri 必须在本机编译 Rust。编译过程中 Tauri 自己的一个构建脚本被拦，报 4551。

这里分清了两件完全不同的事：

- **发布问题**：以后别人装 gogoke，他们的电脑上也可能开着智能应用控制，未签名的安装包可能被拦
- **开发问题**：这台电脑上根本编译不出来

### 09:03　Owner：「像 sandglass 就已经不用考虑签名的问题了」

查 Sandglass 的做法，确认它**有意不签名**：安装包和便携包都明确标 unsigned；防篡改靠 **Owner 自己签的校验清单**；README 如实写明"开着智能应用控制可能被拦，不要为此关系统安全功能"。仓库里准备过 SignPath 免费开源签名，但**不依赖它**。

**结论：发布问题照 Sandglass 办，签名不是前提。**

但 Sandglass 自己平时是用 Python **从源码运行**的，就像房间用 Node 跑源码——**它不需要在本机编译**。Tauri 不一样。所以**开发问题还没解决**。

### 09:11　Owner：「不能把 Tauri 换掉么」→ 试 Electron

Electron 的主程序是装依赖时直接下载的**现成签名文件**，我们的代码全是 JS——跟房间一样"用签名运行时跑源码"，**完全避开本机编译**。实测空 Electron 在本机能跑、没被拦。

代价是把 CodexMonitor 后台的 **125 个 Rust 功能全部移植到 Node**，安装包也大得多。

当时比较过的其它方案（浏览器/PWA、NW.js、Neutralino、Wails、.NET、Flutter）要么要本机编译、要么功能不全、要么得扔掉那套 React 界面，都被排除。

### 同一天　Codex 证明了更省的路：Tauri 留着，编译挪到云端

Codex 在自己的分支上（04:12–13:03，20 个提交）做出了 gogoke：

- **保留 Tauri**，不移植那 125 个功能
- **编译放到 GitHub Actions 的 Windows 云服务器上**——那里不开智能应用控制
- 套上 **Sandglass 式的更新链**
- 装到了 Owner 本机 `%LOCALAPPDATA%\Programs\gogoke`，版本 0.1.2

这等于**同时解决了开发和发布两个问题，而且不用换框架**。

### 21:33　Owner：删掉 Electron 那条线

Electron 路线正式放弃。之后 Owner 说："壳已经弄好了，基本内化完了，现在就是怎么把我们的东西填进去了。"

## 四、每一个选择的理由

### 为什么是 CodexMonitor

现成、完整、Owner 看着对；MIT；支持 Windows；有中文界面源码。**要的是一个看得见的成品当底座，而不是让 agent 猜。**

### 为什么保留 Tauri，不换 Electron

换 Electron 唯一的收益是"不用在本机编译 Rust"。**云端编译拿到了同样的收益，而不用移植 125 个功能。** Electron 的代价（移植、体积、内存）就没理由付了。

另有一条实测旁证：Electron 的 GPU 进程在 exe 路径超过约 188 个字符时会崩溃——而这台机器上的工作树路径普遍很长。

### 为什么在云端编译

**因为这台机器编译不了，而且编译不编得过不可预测。** GitHub Actions 的 `windows-latest` 不开智能应用控制；那里编出来的程序装到本机，截至目前未被拦。

**本机只做两件事：运行装好的产品，以及用签名运行时跑脚本。本机不是 gogoke 原生代码的编译场。**

### 为什么不买代码签名证书

Owner 的立场（2026-09-15）：**像 Sandglass 一样，不用考虑签名问题。**

理由是两个问题必须分开：

| 问题 | 靠什么解决 |
|---|---|
| **这次下载的东西是不是 Owner 发的、有没有被篡改** | Owner 离线签名的校验清单 |
| **Windows 认不认识这个发布者** | 代码签名证书 |

gogoke 自己的文档原话："**Windows publisher reputation and gogoke release authorization are different questions.**"

前者是安全问题，必须有；后者是兼容性问题，**当前不作为发布前提**，但它会导致别人的机器（以及子进程，见第一节第 4 条）被拦。**SignPath OV 是已验证可行的补救路径**，随时可以加，但不是前提。

### 为什么要自己的更新链，而不是让用户每次手动下载

- 更新必须经过**同一把 Owner 公钥**校验才会安装，保证每一次升级都是 Owner 授权的
- 未签名程序每次重新下载都要重新面对智能应用控制；**应用内更新走受控路径**
- 失败必须能回滚，**用户数据不能跟着程序目录一起丢**

## 五、更新链怎么运作

完整说明见 `apps/desktop/docs/release-integrity.md`。要点：

**发布**
1. CI 在云端产出：`gogoke-<ver>-windows-x64-unsigned-setup.exe`、便携 ZIP、`SHA256SUMS.windows`
2. Owner 在**自己机器上离线**用 `tools/sign-gogoke-release-manifest.ps1` 签清单。私钥 P-256，默认在 `%USERPROFILE%\.gogoke\release-key.txt`，**绝不进仓库、构建树、CI、发布资产**。只有公钥编译进程序（`apps/desktop/src-tauri/gogoke-release-public-key.txt`）
3. `tools/publish-gogoke-release.ps1` 核对 CI 产物、重算哈希、签名、用内置公钥验签。**默认到此为止**，真正发布要显式加 `-Publish` 和发布说明文件——**发布是人做的动作**

**CI 自己也守门**：`gogoke-desktop.yml` 的 "Check release trust boundary" 步骤要求公钥是合法 P-256 格式，并且**任何像私钥的文件被 git 跟踪就直接失败**。

**更新**
1. 只认 `taiyun668/gogoke`；只接受一个更新的、非草稿、非预发布版本；安装包、清单、签名三个文件名必须精确匹配
2. **签名把清单绑到 Owner；清单把版本和安装包 SHA-256 绑在一起**
3. 先下载到应用缓存、算哈希，**对上了才提示更新**
4. 用户确认后重新拉取并验证签名身份、重新哈希缓存的安装包，启动独立的更新协调器后退出
5. 协调器持有文件锁、等旧进程退出、**把整个旧安装挪开**、运行可见的安装程序、启动新程序
6. 新界面首次渲染后写一个**绑定版本号的就绪回执**，之后才删备份
7. 安装失败、提前退出、版本不对、没有就绪回执——**恢复旧安装**并记录有界的失败日志

**信任根编译在程序里，不可配置**：允许的下载主机列表是 `const`，公钥是 `include_str!`。**任何"从数据/配置导入允许主机或公钥"的设计都是后门，禁止。**

**数据与程序分离**：用户数据在独立的 `app.gogoke.desktop` 身份下，不在安装目录里。替换或回滚程序文件，不会动项目数据和设置。

**0.1.2 的教训**：0.1.1 发布后，GitHub 换了发布资产的下载域名，旧版按白名单拒绝下载，**无法自我升级**。0.1.2 把 `release-assets.githubusercontent.com` 加进白名单，需要一次**手动引导安装**，此后应用内更新才恢复。**白名单是编译期常量，改它就是发新版。**

## 六、长期规则

以下条款约束所有阶段、所有施工者，**不随任何一个计划结束而失效**。

**必须**

1. **gogoke 的任何原生代码（Rust、C、任何会产出 exe/dll 的东西）一律在云端 CI 编译和测试。** 新增 crate、新增可执行文件、新增原生测试，**必须同时接进云端流水线**
2. **新增任何会被 gogoke 启动的可执行文件（子进程），必须在引入时写明它在智能应用控制下的处境**。发布不做代码签名（Owner 2026-09-23 决定，沿用现有更新链）；该组件是否可用，以 Owner 实机上由正式安装包实际拉起的结果为准
3. **任何计划只要涉及构建、测试、发布、更新或新增可执行文件，必须引用本文件**
4. 更新链的信任根（公钥、允许主机、协调器）保持**编译期常量**
5. **每个流水线的每个 job 都必须设 `timeout-minutes`**，同一分支有新推送时取消旧运行（`concurrency` + `cancel-in-progress`）
6. **公开仓库中已提交的文件一律不含本机绝对路径、用户名、账户用量快照、令牌或私钥**，由流水线机械检查（检查器带正向样本）。路径用仓库相对路径或 `%USERPROFILE%`、`%LOCALAPPDATA%` 占位

**禁止**

7. **在 Owner 这台机器上编译 gogoke 的原生代码并把结果当作证据**——**包括云端不可用的时候**。本机的原生编译结果混着"代码对不对"和"智能应用控制放不放"两件事，而后者不可解释
8. **关闭、绕过、修改智能应用控制或任何系统安全设置**——无论是为了开发、测试还是安装。施工方与复核方都不得触碰
9. **从一个程序的放行推断另一个程序或下一个版本也会放行**
10. 私钥进入仓库、构建树、CI 或发布资产
11. 让允许主机、公钥或信任根可以从数据、配置或迁移中导入
12. 替 Owner 处理 GitHub 付款、额度或账户设置

**可以**

13. 在本机用**签名的运行时**（官方 `node.exe`、`python.exe`）跑脚本和 JS/TS 测试——这是房间和 Sandglass 一直在用的方式，不受影响
14. 在本机运行**云端构建、正式安装**的 gogoke

## 九、反例：2026-09 的 S1-R4 施工是怎么偏的

**两件事叠在了一起。**

**第一件：这条规则当时只活在一份记忆笔记和一个流水线文件的存在里，从没写进任何计划。** S1-R4 为了 Route B（数据库权威归 Rust）新建了一个**独立的 Rust crate** `apps/desktop/native-host`。云端流水线 `gogoke-desktop.yml` 只编 Tauri 应用本身，**从来不编、不测 native-host**。计划的 RUNBOOK 写的是"native-host：`cargo test`……Windows 实际编译/测试"，被照字面理解成"在这台 Windows 上编"。

**第二件：云端本身停了。** GitHub Actions 在 2026-09-19 晚起因账户付款或支出上限问题**全部拒绝启动**（`steps=0`，"recent account payments have failed or your spending limit needs to be increased"）。最后一次成功的运行是 **2026-09-18 23:22Z**。

**施工方其实做了对的那一步**：2026-09-20 起在 `codex/gpt-*` 分支上新建了云端 native 证据流水线（`gogoke-s1-r4-controlled.yml` 于 09-20 14:20、`gogoke-s1-r4-native-evidence.yml` 于 09-20 19:18），20、21 日至少四次运行——**全部在分配 runner 之前就被付款问题拦下，一步都没执行**。云端路走不通，本机就成了唯一能编的地方，于是撞上智能应用控制。

本机拦截的日期分布印证了这一点：

```
09-15   27 次   当初本机编 Tauri → 改为云端构建
09-16~18  0 次   云端路线正常工作
09-19   14 次   云端停摆的同一天，本机原生编译重新出现
09-20~22 58 次
```

（09-19 当天本机编译与云端停摆哪个在先，两者相隔不到一小时，**不作因果推断**。）

结果（截至 2026-09-22）：

```
155 个检查点中 102 个记录了 4551 拦截
所有真实子进程测试轴：执行次数 0

本机强制拦截按文件统计：
  24 次  build-script-build.exe         本地 Cargo 构建脚本
  16 次  gogoke_native_host-*.exe       本地 cargo test 程序
  20+次  thiserror_impl / serde_derive … 本地过程宏 DLL
   3 次  gogoke-root-lock-probe.exe
   0 次  %LOCALAPPDATA%\Programs\gogoke  ← 云端构建、正式安装的产品
```

更深一层：**Node 那一半在本机没问题**（签名运行时），**被拦的恰好是 Route B 让它成为数据库权威的那一个 Rust 组件**。换发动机把一个编译型二进制放回了本机开发循环的关键路径上——Route B 本身是对的，**但云端编译的规矩没有跟着它走**。

**两条教训：**

1. **约束必须写成长期规则，不能只活在记忆和某个文件的存在里。计划一加新组件，约束就会漏。** 这就是这份文档存在的原因。
2. **"只在云端编译"意味着云端一停，原生证据就该停，而不是改道本机。** 本机结果混着"代码对不对"和"智能应用控制放不放"，拿它顶替只会得到一堆不可复现的数字。2026-09-22 Controller 在 MC-158 的处理是对的：云端 job 被付款拦下后，**不重试、不改道本机，原生相关标 BLOCKED，只继续不依赖原生的工作**。这一做法已写入第六节。

## 十、2026-09-22：为什么源码迁到公开仓库

**Sandglass 的云端构建之所以不花钱，是因为 Sandglass 是公开仓库——公开仓库使用 GitHub 标准托管 runner 不计分钟。** 2026-09-15 照搬 Sandglass 做法时，这个前提没有被带过来：gogoke 的源码放在**私有仓库** `gogo-party` 里，Actions 按分钟计费，Windows runner 按 2 倍计。

后果（全部可查）：

- 2026-09-18，`ci.yml` 的 TypeScript 检查步骤在 PR #6 的分支上**卡住不退出**，而流水线**没有设任何 `timeout-minutes`**，每次都挂到 GitHub 默认的 6 小时上限（实测 361 分钟后被取消）。一天之内反复触发，消耗 **3,355 分钟 Windows 时间**（按 2 倍计约 6,700）
- Owner 的 GitHub Pro 包含的分钟数被耗尽；支出上限为 0，自 2026-09-19 晚起**所有流水线拒绝启动**，包括产品构建流水线
- 同样的卡死在 2026-09-15 已出现过（两次运行挂了四个多小时，被手动取消），当时只停了任务，没有修根因

**Owner 的决定（2026-09-22）：不额外付费；gogoke 源码迁入已有的公开仓库 `taiyun668/gogoke`，许可证 MIT。**

理由（Owner 原话）：「我们现在用的所有的都是来自开源的公开仓库包括壳，凭什么不公开」——CodexMonitor 与 T3 Code 均为 MIT，SQLite 为公有领域。

**为什么是 `taiyun668/gogoke` 而不是另开新仓库**：它已经是公开的发布渠道，**已安装的 gogoke 编译时写死的更新源就是这个仓库**。源码、云端构建、发布放在同一个公开仓库，Actions 免费，已安装副本的更新不中断。换一个新仓库名并把发布挪过去，已安装的 0.1.2 将收不到更新，需要手动重装（0.1.2 白名单那次的同类教训）。

**迁移的原则**

- **新历史，不带私有仓库的历史**。`gogo-party` 的检查点里有大量本机绝对路径和用户名，历史一旦公开无法收回
- 只放产品需要的文件；施工计划、检查点、`packages/`、`crates/`、`.agents/skills/`（含 Apple HIG 复制内容，不得再分发）不进公开仓库
- 公开前补齐 `THIRD_PARTY_NOTICES`（MIT 的唯一要求是保留署名）
- 在已有 `main` 上**追加提交**，不强推、不动已有的发布与标签
- 公开仓库的已提交文件里**不得出现本机绝对路径、用户名、令牌、私钥**；扫描器必须先在已知含敏感内容的样本上命中，证明不是空跑

**施工也在公开仓库进行（Owner，2026-09-22）。** 迁移完成后，施工分支、检查点、计划、复核记录、WIP 提交都进入 `taiyun668/gogoke`，全部公开。`gogo-party` 转为只读存档，不再推送。

由此带来的硬要求：

- **进入公开仓库的文件一律不写本机绝对路径、用户名、账户用量快照。** 路径用仓库相对路径，或 `%USERPROFILE%`、`%LOCALAPPDATA%` 这类占位。2026-09 以前的检查点每一个都含 Windows 用户目录下带用户名的完整路径，这个习惯必须断掉
- **由流水线机械检查，不靠自觉。** 公开仓库设一个与"Check release trust boundary"同类的检查：已提交文件中出现本机绝对路径、用户名、令牌、私钥格式即失败。检查器必须带一个正向样本，证明它会失败
- **WIP 规则照旧**，但 WIP 提交同样公开，同样受上述检查约束
- 旧检查点留在私有存档；公开仓库里的检查点序列从一个**承接检查点**开始，只写门状态、候选、在飞工作与未决项，引用存档而不复制其中的本机细节

**公开仓库仍然要设超时**：免费不等于可以卡。一个挂满 6 小时的 job 会占住并发名额，其他证据只能排队。第六节的规则在公开仓库同样适用。
