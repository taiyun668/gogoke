# gogoke 事实账本决定：沿用 Git 与 GitHub

- 决定人：Owner
- 日期：2026-09-23
- 状态：已定，后续计划与施工以此为准

## 决定

**gogoke 的事实账本沿用 Git 与 GitHub。本机数据库只负责活跃协调。**

这是 GOGO PARTY 产品章程中已有的决议，这次明确延续到 gogoke。章程原文：

- 第 5.1 节："repository-backed 不表示'只用 Git 作为数据库'。Git 保存可审阅、可交换的事实账本；活跃任务的 claim、lease、command 和消费位点由持久协调数据库保证原子性。"
- 第 4.3 节，产品不负责："替代 Git、GitHub、CI、IDE 或模型供应商"。

## 为什么要写下来

S1-R4 的架构写成了"所有 Project/Seat/Grant/Context/Decision/Outcome/Dream 记录进入同一个 SQLite 事务域"，没有保留章程的这条分工。这是迁移到 gogoke 时丢掉的决议，不是新做的取舍。

另一方面，公开仓库迁移后的施工本身，已经验证了 Git 与 GitHub 能承担事实账本：
- 成果以 PR 呈现，有版本、可指认；
- "merged_by = taiyun668" 就是 Owner 的认可，不可篡改；
- CI 运行记录就是验证证据；
- 检查点与复核记录都在仓库里，可审阅、可交换。

## 分工

| 归 Git / GitHub（事实账本） | 归本机数据库（活跃协调） |
| --- | --- |
| 已被接受的成果、事实、决定与其证据 | 进行中的派发、认领、租约、命令与幂等 |
| 采用 / 验收：以 PR 合并与合并人为准 | Session、进程托管与投递的实时状态 |
| 验证证据：以 CI 运行记录与内容哈希为准 | 容量许可、重试、消费位点 |
| 审计与复核记录 | 尚未提交为事实的草稿与提案 |

原则：
- 数据库里的记录是**工作状态**，不是事实。一件事只有进入 Git，或经 GitHub 合并，才算被接受。
- 同一个事实不在数据库和 Git 各维护一份权威版本。数据库可以保存指向 Git 提交或 PR 的引用，以及用于加速的缓存。
- 数据库丢失或损坏时，已接受的事实必须能从 Git 恢复。
- 不在本机重建 Git / GitHub 已提供的能力：版本历史、合并与合并人、CI 证据、审阅记录。

## 对施工的要求

1. S1-R4 计划与架构按上表修订：
   - Context / Decision / Outcome / Evaluation / Dream 中属于"已接受事实"的部分，改为投影到仓库；
   - 本机数据库收窄为活跃协调。
   修订按计划规则处理：涉及权威 / 内核的改动，由设计方出修订。
2. 已建成的部分不盲目拆除。逐项判断：留作活跃协调，改为缓存 / 引用，或移除。结论写入检查点。
3. 计划修订会改变计划 MANIFEST。按公开授权文件的规则，现有授权会随之过期，需要 Owner 重新合并新的授权文件。
