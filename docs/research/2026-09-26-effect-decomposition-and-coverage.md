# 从效果倒推：要解决的问题与调研覆盖

- 日期：2026-09-26
- 性质：调研的问题清单和覆盖表。它不给结论。
- 为什么写这份：前几轮调研是照着"有哪些材料"组织的，没有从 Owner 要的效果出发，所以架构层面的问题基本没查到（见[执行层对照 §3b](2026-09-26-execution-layer-capability-table.md)）。从这份开始，每个调研问题都必须能沿着这条链追回到一个效果：**效果 → 由谁实现 → 它属于哪一层 → 要解决的问题 → 调研问题**。
- 效果的来源：
  - [GOGO 要什么](../design/GOGO-要什么.md)（Owner 2026-09-16 口述）；
  - [要做的和不做的](../design/GOGO-要做的和不做的.md)；
  - [产品章程](../design/00-product-charter.md)；
  - [方向候选](../directions/2026-09-23-direction-candidates.md)；
  - [会话、记忆与做梦架构](../directions/2026-09-23-session-memory-dream-architecture.md)；
  - AGENTS.md 的宗旨"把人从环里拿掉"。
- 覆盖程度分三档：
  - **未查**：没人查过；
  - **表面**：只知道有这么个东西，或者只看到问题现象、零件、界面形状；
  - **架构层**：查到了别人的数据模型、谁做决定、状态放在哪，而且有源码或一手文档作证。

## E1 旁聊窗口与递话

- **形态**（Owner 2026-09-26 补充，见[要做的和不做的 §七](../design/GOGO-要做的和不做的.md)）：旁聊是一个窗口，不是一个岗位。它跟 Codex 桌面端的 `/side` 一模一样，只是把"选模型"换成"选角色 + 实例"。旁聊要 fork 主控的上下文。审计和秘书长也不只绑在这个窗口上。
- **要解决的问题**：
  0. 机制直接照搬 Codex 的侧边聊天，不需要"选中一句再递过去"这一步（Owner 2026-09-26 更正）。所以先要把 Codex 旁聊的实际机制读清楚：fork 了什么、结果怎么回到主线。
  1. 怎么 fork 主控上下文：同厂商原生 fork，还是跨厂商转录或重放？"角色 + 实例"换成另一家时，fork 出来的内容损失多少？
  2. fork 出来的会话怎么隔离：fork 时带什么权限（只读，不能改工作区）。
  3. 旁聊会话留多久：Codex 的旁聊是临时的，关掉 app 就没了，社区有人要求把它持久化成主线程的子线程（openai/codex #26227）。
  5. fork 出来的旁聊不是正式审计：同一个审计角色，在旁聊里是 fork 会话，做正式审计时是零继承的干净会话。这两种会话要能区分开。
  6. 全局和项目两层：秘书长属于全局，审计属于项目，两者都能拉进同一个旁聊窗口。各自的会话存在哪里，fork 谁的上下文。
- **调研问题**：
  - 别人的旁聊和 fork 在架构上怎么实现：fork 出来的上下文是只读引用，还是一份拷贝？怎么让它不回写主线？怎么持久化？怎么把结论拉回主线？
  - 跨引擎的 fork 或交接，实际能带过去什么？
- **覆盖**：
  - 产品形态已找到对标：Codex `/side` 和 `/fork`、Cursor Side Chats、Claude Code 与 VS Code 的 `/btw`（见[对标清单](2026-09-26-benchmarks.md)）。
  - 实现：未查。
  - 跨引擎交接只知道 claw-orchestrator 的做法：把文字对话重放进新引擎，不带工具轨迹。

## E15 秘书长：你与主控、审计之间的桥梁

- **形态**（Owner 2026-09-26）：秘书长不只是一个称呼。你通过它跟主控、审计对接，这是基本操作；它还有很多别的职能，对标 Grok Bot 的"幕僚长"。
- **要解决的问题**：
  1. 秘书长能对主控、审计做什么：转达、派任务卡、追进度、汇总。它的权限边界在哪：不进仓库写代码，不直接指挥工人。
  2. 跨项目看得到什么：只看上报的摘要，还是能读原始材料？项目隔离由谁来守？
  3. 幕僚长的职能怎么落地：统筹多项目的优先级，替你分拣要你定的事，管理其他 agent。
  4. 它自己的全局记忆，跟项目记忆怎么分开。
- **调研问题**：Grok Bot 的幕僚长怎么通过共享线程协调各个专职 agent？别的"总助"产品，权限和记忆是怎么划分的？
- **覆盖**：未查。只知道 Grok Bot 有这个模式（2026-08 发布 beta）。

## E2 角色和实例解耦（角色 → 席位 → 实例 → 进程）

- **谁**：所有席位。角色管理在侧窗，实例管理在设置里（全局）。
- **要解决的问题**：
  1. 角色定义放在哪里、怎么管版本。它就是固定前缀的来源。
  2. 席位身份和会话分开：换厂商、换账号、换会话时，席位不变。
  3. 数量关系：一个角色能不能同时有多个实例？一个实例能不能兼任两个角色？比如审计不能兼施工。
  4. 同一个实例服务不同项目的席位时，资料、记忆、执行权都不能共享，隔离怎么做。
  5. 记忆归谁：席位记忆随席位延续，不随会话。
  6. 权限跟角色走，还是跟实例走。
  7. 共享的实例容量怎么在多个项目之间分配：设计 21 要求先拿到原子的、可恢复的许可。
- **Owner 2026-09-26 补充**：同一个实例可以开多个会话，同时服务多个角色或项目，做好隔离即可，就像 ChatGPT 的 Project 独享上下文。角色体系可以借鉴"三省六部"。主控下辖的角色不能直接找你。
- **调研问题**：
  - 别人有没有把角色、身份、会话、进程分成几层？
  - 三省六部（edict）的角色分工和"封驳"审核，在架构上怎么落地？
  - 实例替换时，记忆和权限怎么处理？
  - 多项目共用一个账号时怎么隔离？
- **覆盖**：
  - 表面。只知道 Paseo 是一个 agent 对应一个会话、它的 profile 更像角色（执行层对照 §3b）；Orca 按账号托管家目录，只看到文件名这一层（底座拆解 §4）。
  - 分层模型、实例替换、跨项目共用一个账号，都没查。

## E3 只跟主控说话，席位不直接找我

- **谁**：主控是唯一的出口，其余席位都对主控负责。
- **要解决的问题**：
  1. 席位的问题、失败、卡住怎么汇到主控；主控答不了，才转成"要你定的一下"。
  2. 真实的 CLI 问题（权限请求、`userInput`）怎么从施工席位一路路由到主控，再到你。答复又怎么原路送回去。
  3. 主控自己答的那部分怎么留痕，你能不能事后查。
- **调研问题**：
  - 多 agent 产品里，子 agent 的权限请求和提问是由上级 agent 代答、直接找人，还是按规则自动处理？代答的边界怎么定？
- **覆盖**：
  - 表面。适配层知道各家有权限请求和提问事件（执行层对照 §2）；Paseo 的 Codex 通道能把审批交给一个自动审查子 agent（底座拆解 §2）。
  - "上级代答"的架构没查。

## E4 主控在授权范围内自主拉席位、拉角色

- **谁**：主控。
- **要解决的问题**：
  1. 授权范围怎么表达，由谁来检查：能用哪些厂商和账号、能开多少、能碰哪些路径和动作。
  2. 越界时默认安全停下，而不是来问你。
  3. 派活怎么切：按写入范围切、先冻结接口、每一块各自验收（方向候选 §3）。
  4. 拉起来的席位怎么回收、怎么判断它还活着。
- **调研问题**：
  - 别人让 agent 开 agent 时，权限和配额怎么约束？
  - 切活和写入范围租约是怎么实现的？
- **覆盖**：
  - 表面。
    - 论文层面知道多 agent 协作的代价（底稿 §9.1）；
    - 零件层面知道 hcom 这类 agent 间通信（零件拆解 §5）；
    - Paseo 对外提供开 agent 的 MCP 工具（执行层对照 §3b）。
  - 授权表达和写入范围租约，都没查到架构层。

## E5 正在进行，一眼看全，同时开几个项目

- **谁**：主控的输出流，左栏、秘书长。
- **要解决的问题**：
  1. "谁在做什么"的状态从哪里来：是各席位的事件，还是主控的汇报？
  2. 同时开几个项目、切走不停：控制宿主的生命周期不等于窗口（设计 20），多项目时状态怎么汇总。
  3. 未读、待处理这些标记放在哪一层。
- **调研问题**：
  - 多项目、多 agent 的状态汇总由谁负责？
  - 守护进程和窗口怎么分离？
- **覆盖**：
  - 界面层已查（`gogo-ui-2026-09-13/` 五家产品研究、工作主路径）。
  - 状态汇总的架构：表面。Orca 和 Superset 有守护进程、冷恢复（底座拆解 §1），只看到文件名。

## E6 成果本体：带版本，能指着说哪里不对

## E7 喊停就停，不知道就说不知道

- **谁**：执行层、主控。
- **要解决的问题**：
  1. 停止要传到每个席位、每个进程，还要确认真的停下了。
  2. 投递没收到回执、用量没返回、停了没确认，这几种"未知"要分开表示，并且能看到。
  3. 断线后再接上，恢复出来的状态要如实。
- **调研问题**：别人怎么表达投递和停止的"未知"状态？怎么确认已经停下？
- **覆盖**：
  - 问题侧已查：长时间无人值守会怎样出错（底稿 §1）。
  - 自家实现已有：进程托管（R2-06a）、`seat-runtime` 的投递追踪。
  - 别人的做法：未查。

## E8 审计独立、干净

- **谁**：项目审计席，复核方。
- **要解决的问题**：
  1. 零继承怎么强制做到，而不是靠自觉。
  2. 审计最好换一家厂商：这取决于多家适配。
  3. 侧聊里的私话不能进入主控委托的那份审查。
- **调研问题**：别人怎么在架构上保证审计会话干净、结论不被污染？
- **覆盖**：
  - 为什么必须独立：已查到论文层，比如自我偏好（底稿 §0.4、§9.3）。
  - 实现层：表面。Paseo 有第二意见 skill（执行层对照 §3b）。

## E9 交接靠仓库，不靠转述；几种"完成"严格分开

- **谁**：所有席位之间，席位和你之间。
- **要解决的问题**：
  1. 交接包从提交和检查点机械提取，保留走过的死路。
  2. "跑完了""做好了""改动已落到你手上"分别对应系统里哪几个状态，由谁来改。
- **调研问题**：别人的交接包是怎么产生、怎么验证的？

## E11 多厂商、多账号，额度当调度资源，不怕厂商变

- **谁**：调度，实例管理。
- **要解决的问题**：
  1. 读到每个账号的剩余额度和恢复时间。
  2. 按额度派活：谁来决定，在哪一层决定。
  3. 厂商一变（改协议、改模型、停服），能不能察觉、怎么降级。
  4. 执行目标不能被悄悄替换，运行中的东西要自己报出实际身份。
- **调研问题**：
  - 有没有产品真的按额度调度？
  - 厂商变化是怎么被察觉的？
- **覆盖**：
  - 读额度的接口：零件层已查（底座拆解 §3）。
  - 厂商机制和额度的事实：已查（底稿 §2）。
  - 按额度调度：未查。Paseo 只显示额度，不拿它调度（执行层对照 §3b）。
  - 适配能力：已查（执行层对照 §2）。

## E12 越做越少找我：决定登记、分阶段放权、反射

- **谁**：主控的判断后端（Jev），Owner 决定登记册。
- **要解决的问题**：
  1. 你的决定变成一等对象，新方案出来时自动对照，冲突先拦下。
  2. 放权按判断类别分阶段进行，由校准数据驱动；换版本时用回放重新校准。
  3. 每个机制都写明它护的是什么、什么时候结束（评判 N1）。
- **调研问题**：
  - 别人的决定登记、分阶段放权、判断校准，在架构上怎么做？
  - 成熟行业（航空、医疗、金融）的放权范式，怎么落到系统结构上？
- **覆盖**：
  - 表面。
    - 零件层有 AsDecided（零件拆解 §3）；
    - 成熟范式只到"有这回事"（底稿 §6）；
    - NaveHQ 的蓝图是我们自己的。
  - 架构层：未查。
