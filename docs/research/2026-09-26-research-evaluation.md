## 0. 尺子

按 Owner 已经定下的顺序量：

1. **宗旨**：把 Owner 从环里拿掉。每条发现先问三件事：它能减少 Owner 触点吗？它说明哪里不能拿掉人吗？如果不能，那一步应该让系统安全停下，还是交给 Owner？
2. **产品定位**：一个人指挥一支 AI 团队建设、经营多个业务；首版只做代码生产；任何一处都不得假设 Owner 一直看着。
3. **编排引擎的一票否决**：必须驱动现成 CLI、走订阅额度；必须可以交互接管。
4. **系统六条**：席位不直接找 Owner；三种"完成"分开；交接交仓库里的东西；审计必须是干净会话；不知道就说不知道；不替模型出题，也不替 Owner 做决定。

## 1. 结论先说

1. **方向没有错，但有一处地基级缺口：授权来源会丢。**
   - 压缩、交接、记忆整理，都会把"谁授权了什么"洗掉。底稿 §0.1 的数据：写进记忆后，执行端照做的比例高达 98.6%。
   - 这正是 gogoke 近期返工的头号原因：账本分工、构建约束、签名方式，这些 Owner 已经做过的决定，一再被重新加回来。
   - 要把 Owner 拿出环，前提是系统自己记得 Owner 授权过什么，并且这份记录在压缩和交接之后仍然成立。建议列为下一阶段第一优先。
2. **把 Owner 拿出环，靠的不是"人随时能接管"。** 底稿 §0.5 的航空和驾驶事故说明，平时不在环里的人，接管时往往接不住。所以系统遇到超出边界的情况，默认动作应该是**安全停下并写明原因**，而不是把球丢给 Owner。这与宗旨一致，并且让"Owner 不必一直看着"这件事变得安全。
3. **复核要换人、要盲、要结构化，而且要设在交接处，不能只放在最后。**
   - 同一家模型自己写、自己审，是单一盲点；不看"谁写的"，自我偏好就消失；多个 agent 讨论会互相附和，结构化应答能把附和率压到 9%；在交接边界设闸门，幻觉存活率从 58.4% 降到 16.2%，只在末端检查仅改善 2.3pp（底稿 §9.3）。
   - 已有设计里的"审计必须是干净会话"和"审计可以是另一家"方向是对的。缺的是：盲评、结构化应答，以及在每个交接点设机械闸门。
4. **执行层：建议继续用自己已有的薄层，按需搬别人的零件，不整体换底座。** 理由见 §4。这仍然是 Owner 的决定；§4 列出了一项能改变这个结论的核查。
5. **自家历史给了一条反向纪律。** NaveHQ 和 gogo-party 都是治理先于产品、而且自我增殖；Sandglass 两周发了十一个版本。今后新加的每一个机制，都要说清楚它保护什么，以及它在什么条件下结束。
6. **业务域揭示了一个"不知道自己想要"的事实：顾客那一侧的"转人工"，在一人公司里会落到 Owner 头上。**
   - 国标 GB/T 47746、拼多多"第三方自动回复不计入回复率"、亚马逊"自动回复不算回复"，都要求有人在。
   - 这件事要在立项时就定：谁来当这个人，或者这个业务先不做实时客服。不能等上线后才发现。

## 2. 逐项评判：与已有设计的关系

分三类：**印证**（已有设计是对的，保留）、**补强**（方向对，缺一块）、**新增**（已有设计没有覆盖）。

### 2.1 印证

| 已有设计 | 支持它的证据 |
|---|---|
| 事实在 Git，会话只是缓存（章程 §5.1；会话记忆 §2） | 压缩和整理会洗掉授权、丢掉堆栈（底稿 §0.1、§1.3）。只有进了仓库的东西，经过压缩之后仍然可信 |
| 审计必须是干净会话，可以换一家 | 自我偏好、信度高但效度低、自审最终塌缩成橡皮图章（底稿 §0.4、§9.3） |
| 执行目标不得被静默替换（设计 19，章程 §3.13） | 厂商真的会换：Claude Code 钉死的模型被静默覆盖、默认模型被静默升级；Opus 5.5 按内容回退到别的模型；今天 Codex 故障时客户端自动退回 GPT-5.6（底稿 §0.6） |
| 多厂商是常态，不是过渡（章程 §1） | Gemini CLI 停止服务个人订阅、Pro 20x 暂停新购、Sora API 停服、Vibe Kanban 停运、Roo Code 归档（底稿 §0.6、§3.5；业务 §0.4） |
| 额度是调度资源（方向候选 §4，设计 21） | 这件事做得到：Paseo 读的就是各家 CLI 本地凭证对应的用量接口，Orca 按账号取用量（底座 §3） |
| 两级家目录、按账号隔离凭证（要做的和不做的 §四） | 一次性 refresh token 会让共用账号的两个程序互相把对方作废；Orca 专门为此做了按账号托管 home，并迁移掉旧的共享凭证（底稿 §1.4；底座 §4） |
| 做梦不得改规则、偏好、权限（会话记忆 §9） | AI 自己写的规则文件有害（NaveHQ 坑库）；记忆整理会剥离授权（底稿 §0.1） |
| 编排决策不交给 LLM（Jev 是在代码列出的合法分支里选） | microsoft/conductor 用 YAML 做确定性路由；Agentless 不给 LLM 流程控制权（底座 §1；底稿 §3.4） |

### 2.2 补强

**B1. 授权来源（第一优先）。**
- 方向候选 §4 已经有"Owner 决定登记册"，但它只被当作"防止返工"的工具。评判：它应该是**授权的唯一来源**。
- 每条记忆、每个交接包、每份计划条目，都要带上"授权来自哪条 Owner 决定"的标签，并且标签和内容一起持久化。论文给出的缓解手段正是这个：越权动作率 16.9% → 0%（底稿 §9.3）。
- 引用不到登记册的，一律当作"未授权提议"。它能进仓库，但不能驱动任何动作。
- 效果：Owner 不用再一遍遍重申已经做过的决定，这本身就是减少触点。

**B2. 交接处的机械闸门。**
- 已有设计里的"测试的 PASS 不替代退出状态"（V0.12 §10.2）和"绿色状态必须绑定证据"（章程 §5.5）方向正确。
- 补一条：**每个交接点**（施工交给主控、主控交给审计、审计意见回流）都要跑与模型无关的检查：编译、类型、测试退出码、改动范围是否越界。不要只在合并前检查一次。
- 依据：末端检查只改善 2.3pp，交接处设闸门能改善约 42pp。

**B3. 按功能分别放权，并让系统显示当前模式。**
- Jev 的"分阶段放权"（方向候选 §1）方向正确。外部范式补充了两点：
  - 放权要分**功能**，不是一根轴。采集、分析、决策、执行各自定级；能力等级和被允许的自主等级分开定（底稿 §5.2、§6）。
  - 飞机自动驾驶的规矩（14 CFR §25.1329）：必须显示当前模式、快速断开、断开时有独特的告警。对应到 gogoke：
    - 界面上显示"哪些判断现在是自动的"；
    - 叫停一步到位；
    - 某类判断被收回自动权时，要明确告知。
- Owner 现在已有"你喊停它就停"。缺的是模式显示和收回告知。

**B4. 失败时安全停下，而不是交给人。**
- 对应"GOGO 要什么"里的"任何一处都不得假设 Owner 一直看着"。
- 建议把它变成一条设计规则：超出边界、证据不足、状态未知时，默认动作是停在安全点，写明"停在哪、为什么、要什么才能继续"，然后进入 Owner 的"一眼看全"。不能在 Owner 不在场时硬往前冲，也不能要求 Owner 立刻接管。

**B5. 组队模式的防附和。**
- NaveHQ 的组队模式（panel、red-blue）和 Paseo 的委员会，都可能掉进"互相附和"。
- 规则：先各自独立出结论，再汇总；应答用固定结构（结论、证据、反例）；评审时不告诉评审方谁写的；参与方至少来自两家。

**B6. 空转与烧钱。**
- 已有"额度调度"（方向候选 §4）和"空转判断"（Jev 场景）。
- 补具体的上限：子 agent 扇出深度、单会话轮数、同一失败连续出现的次数。依据：失控任务跑 12 小时、吃掉周额度的一半；递归 hook 烧掉约 5,000 万 token（底稿 §1.2）。
- 还有 S1-R4 自己的数据：主控占了全部输出的 57%，审计循环没有收敛条件（自家史 §5）。

**B7. 删除与不可逆操作。**
- Grok Worker Provider 的六样和 `gogo-win32-authority` 的路径围栏已经覆盖了一大部分。
- 补两条：
  - 校验要在 shell 展开**之后**做；
  - 备份不能和主数据放在同一处，不能同生共死（底稿 §1.1）。

### 2.3 新增

**N1. 每个机制都要说清楚保护什么、何时结束（自家史 §6）。**
- NaveHQ 走到 v13、gogo-party 的校验器比产品还多、S1-R4 做了九轮全轴审计，共同的根源是：机制没有保护对象，也没有收敛条件。
- 建议写进计划规则：新增闸门、审计、检测器时，必须写明它保护的对象和它的结束条件；两样写不出来就不加。
- 这与 AGENTS.md 的"先算路径，再动手"是同一类纪律，不是新的治理层。

**N2. 计划要产出并行图和 Owner 触点预算（方向候选 §5，从 NaveHQ 回读）。**
- 底稿给的新证据：CooperBench 表明，两个 agent 协作做成功率比一个 agent 做两件事**低 30%**；Scaling Agent Systems 表明，有顺序依赖的任务上多 agent 会退化（底稿 §9.1、§9.2）。
- 因此并行不是越多越好。切活时按写入范围切、先冻结接口，这一点方向候选 §3 已经写了，底稿给出了量化的理由。

**N3. 厂商实际在跑哪个模型，要由运行中的东西自己报出来。**
- 设计 19 要求"不静默替换"。底稿说明厂商侧会自己换，比如 Opus 5.5 的回退、Codex 客户端的自动退回。所以光靠"我们不换"是不够的：适配层每一轮都要读取实际使用的模型并记账。读不到就标"未知"，对应系统六条的"不知道就说不知道"。

**N4. 网页额度通道的平台风险。**
- 亚马逊 Agent 政策原文要求 agent 自报身份，不得模仿人、不得绕过验证码（业务 §0.1）。这是亚马逊的规则，不是 OpenAI 的。
- 但趋势是：平台开始写"agent 必须自报身份、不得装人"。网页额度通道（Oracle、codex-chatgpt-web）本质上是驱动网页界面。
- 评判：可以作为补充额度用，但**不应放进关键路径**。在把它纳入额度调度之前，要先核对 OpenAI 服务条款里关于自动化访问的原文（本轮未核，[待]）。

**N5. 领域内核的第一批需求已经出现（方向候选 §6 三层结构）。**
- 业务调研给出的约束，属于"电商领域适配内核"，不属于统一内核：
  - 平台 agent 规则；
  - 中国 AI 生成内容标识（显式加隐式，日志 6 个月）；
  - 欧盟第 50 条；
  - 亚马逊合成人物的 XMP 标记；
  - "图和货一致"的不可生成层。
- 按"不提前抽象"的原则，等第一个业务项目开工时再建。这里只登记，免得到时候漏掉。

## 4. 执行层：自建还是借底座

**事实**（底座拆解）：
- Paseo 在 Claude 上走 Agent SDK，在 Codex 上走 app-server，其余家走 ACP。gogoke 的 `seat-runtime` 用的是**同一组协议**：Codex 走 app-server，Claude 走 stream-json，Grok 走 ACP。代码约 5,000 行，是我们自己的。
- Paseo 能通过两条一票否决：驱动现成 CLI、走订阅额度，也可以交互接管。它多出来的是：35 家以上的驱动、跨家交接、远程与手机、社区维护、额度读取器。
- Orca（MIT，78k★）强在多账号托管和按账号取用量；Multica 和 Superset 的许可证限制嵌入和托管。
- 所有底座都没有事实账本、独立验收、分阶段放权。这三样正是 gogoke 要做的部分。
- 底座会死：Vibe Kanban 停运、Roo Code 归档、Crystal 转手（底稿 §3.5）。

**评判：继续用自己的薄执行层，按需搬零件。**
- 首版要适配五家：Claude Code、Codex、Grok Build、OpenCode、Antigravity。前三家已经有了，另外两家都能走 ACP 或事件流。Paseo 多出来的那 30 家，首版用不上。
- 换底座要重新划分宿主边界：Paseo 是 Electron 加 Node 守护进程，gogoke 是 Tauri。它的子进程在智能应用控制下的处境也要重新验证（AGENTS.md 规定每个新子进程都要写明）。
- 治理层要插进权限请求和事件流。在自己的代码里插，比在别人的守护进程外面包一层更直接。
- 值得直接借的零件：
  - 额度读取：参照 Paseo 调用的五个用量接口；
  - 多账号托管 home：参照 Orca；
  - 跨家转录：CASR；
  - Codex 的 `approvalsReviewer`：用于自动审批。

**能推翻这个结论的一项核查**：列一张能力对照表，把 `seat-runtime` 和 Paseo 在首版五家上逐项对比：启动、续接、分叉、权限请求、用量、中途插话。如果 Paseo 在这五家上明显更全，而且补齐的成本高于接入它的成本，就改为借底座。这张表由施工方按源码填，不需要 Owner 出手。

## 5. 建议的下一阶段顺序

在 R2-05 收口、S1-R4 在 Owner 机器上跑通之后：

1. **Owner 决定登记册加授权标签**（B1）。可以先用文档起步：每条决定一个文件，带编号、日期和适用范围；计划和规则引用它的编号。
2. **交接处的机械闸门**（B2），以及每一轮自报实际在跑的模型（N3）。
3. **额度读取与多账号**：先接 Codex 和 Claude 两家的用量接口，再做额度调度。
4. **计划输出包**：并行图、Owner 触点预算，加上每个机制的保护对象和收敛条件（N1、N2）。
5. **执行层能力对照表**（§4），由 Owner 据此拍板。
6. **Jev 分阶段放权**，同时做模式显示、收回告知和安全停下（B3、B4）。这一项需要前面几项积累的记账数据。
7. 第一个业务项目开工时，再建电商领域内核（N5）。

### 5.1 明确不做

- 没有保护对象或没有收敛条件的闸门、审计、检测器。
- 同一家模型自审，并把它称作审计。
- 只在末端做一次复核。
- 把"人能接管"当作安全兜底。
- 网页额度通道进入关键路径。
- 让 AI 自己写规则文件。

### 5.2 本评判的局限

- 底座只拆到了文件层，没有实际运行过（底座 §6）。
- 业务域里平台规则的后台原文、GB/T 47746 的条款原文，都还没有读到。
- 智能应用控制能否在虚拟机上复现，没有核。

### 5.3 关于调研本身的触点

本轮调研里，Owner 在 Grok、ChatGPT、Gemini 三个网页之间手动发了十几份提示词，并把结果逐份回传。按宗旨，这属于要拿掉的人肉胶水。零件拆解 §1 里的网页额度通道，可以把这一步变成 agent 直接调用。前提是：先核对 N4 里说的条款，而且它只用于调研这类非关键路径。
