# 多 Agent 工作主路径研究

**产品范围说明：GOGO 面向多种成果生产，软件施工与通用生产两套模式并行。软件模式保留 Git、diff 和测试等既有要求，通用模式采用对应成果的审查依据；共用基础交互，允许同项目协作。完整方向见[改版研究总图](revision-map.html)。**

## 1. 结论

面向非程序员的多 Agent 工具，主要工作应围绕三个对象组织：**我正在推进的工作、与主控的对话、能查看和使用的成果**。团队分工、运行过程、技术证据在同一工作里按需展开。底层可以有项目、房间、目标、回合、席位和会话，但不必要求每个人先学会这些名词。

这一判断来自不同产品的共同做法与各自限制：Linear 把工作事项、受托 Agent 和人的责任分开；Lovable、Figma Make、Bolt 把修改反馈贴近预览对象；Replit 明确区分项目容器与产出物；Apple 要求反馈、撤销与引导让人预测自己的操作结果。它们没有共同证明一个唯一的多 Agent 工作流。[S1] [S2] [S3] [S4] [S5] [S6]

对 GOGO，最值得进入下一轮样例验证的四项是：稳定的工作入口；有明确送达时机的底部输入；带版本和位置的成果反馈；能解释停止、断线与恢复边界的就地状态。设计、计划和审计的安排继续由具体项目决定，保留 Owner 最终权威。这里的建议不授权改变当前工程或恢复暂停的施工。

## 2. 参考范围与证据等级

| 参考对象 | 本次核对的机制 | 适合借鉴 | 不据此推断 |
|---|---|---|---|
| Linear | 自定义视图、Inbox、委派、Agent 活动 | 同一工作有多个视图；提醒与任务状态分开；人保留责任 | GOGO 需要照搬企业团队层级或把排活交给 Owner |
| Lovable | 新预览工具条、follow-up、问题、停止 | 指向成果再表达；发送状态贴近输入 | 所有账号已用同一种队列机制；所有直接编辑都免费 |
| Figma Make / Design | 编辑、批量标注、评论截图与版本、版本历史 | 反馈有位置和时间依据；浏览旧成果不等于恢复 | 截图批注一定能可靠定位到当前源码 |
| Replit | 多成果/项目、steer/queue、checkpoint | 发给当前回合与下一回合有区别；恢复范围明确 | 云端完整环境快照可以等价移植到本地多 CLI |
| Bolt | 预览修改暂存、批量应用、历史、项目知识 | 预览尝试与实际改代码分开；命名版本可回找 | 看到预览变化就意味着源码保存或测试通过 |
| Claude Code | 本轮输入、原生 checkpoint 与恢复限制 | 会话、文件和回合有不同恢复范围 | 一次 rewind 能撤掉整个多 Agent 项目的所有改动 |
| Apple HIG | 模态、撤销、进度、首次使用 | 稳定位置、适时展开、可预测操作 | 简洁等于隐藏真实失败或取消所有必要权限边界 |
| Google PAIR | 反馈时机、用户控制、错误恢复 | 告知反馈影响什么、何时生效；失败后有可理解的出路 | 模型能够立即学习每条偏好，或所有错误都能自动恢复 |
| W3C / ACP | 拖动替代操作、状态消息、权限请求身份 | 鼠标/键盘都能完成；原生请求原样回传 | 协议存在就证明 GOGO 适配器已实现 |

AionUi、Cindy、Orca、Herdr、Vibe Kanban 的固定源码研究继续作为团队协作、会话隔离和运行管理的补充，见[五家产品研究](report.html)与[上下文研究](context-map.html)。本次新增证据主要是官方文档与公开协议；Apple 的动态文档另经浏览器读取正文。没有登录这些产品执行付费闭环，因此产品能力按“官方说明”表述；下文的样例是设计实验，不是竞品实测或 GOGO acceptance。

## 3. 用户在管理什么

### 已核对的事实

Linear 的自定义视图来自已有事项的筛选，可保存为列表或看板；更换视图不要求创建另一批任务。委派给 Agent 后，人仍是工作负责人。Inbox 则收纳需要关注的更新，读取、稍后提醒与修改事项是不同操作。[S1] [S2] [S7]

Replit 的一个项目可包含多种成果，并共享数据、后端与发布周期；文档明确指出同项目成果不能独立发布。这个反例说明，用户看到的“放在一起”有时会携带真实工程耦合，不能把目录组织和运行边界混为一谈。[S5]

### 对 GOGO 的判断与建议

“工作”应是前台稳定入口，例如“商城首页改版”。聊天、成果、团队和看板都指向这件工作；开一次审计、换一位施工者或增加一个回合，不自动在 Owner 侧栏多长出一个平级入口。这里是显示层的组织建议，不是新增数据库实体或重命名所有已有 contract。

| 用户看到的东西 | 意义 | 切换时必须保持 |
|---|---|---|
| 项目 | 一组相关工作、资料和运行范围 | 正确项目身份；未发草稿不丢失、不送到另一个项目 |
| 正在推进的工作 | 用户希望得到的一项结果 | 同一目标、主控关系、成果和消息归属 |
| 对话 / 成果 / 看板 | 看同一工作不同方面 | 改布局不改任务状态，不默认换收件人 |
| 团队详情 | 谁在做什么，必要时旁聊 | 旁聊对象明确；内部任务可追查但不强迫用户管理 |

看板可以继续同时提供列表和关系画布。列表服务快速扫描，画布服务关系理解；卡片位置与大小是表达手段，不能隐含改变任务的权限、优先级或验收状态。高亮之外仍需文字或符号，已选对象与运行状态应有不同视觉语义。

**待验证：** 用户能否在没有“房间、席位、回合”教程的情况下，找回昨天的成果、继续同一件工作，并知道新对话是否延续原上下文。若不能，先调整入口与文案，再决定是否需要更多导航层级。

## 4. 怎样控制正在工作的 AI

### 已核对的事实

Replit 区分 steer 与 queue：前者送入活动回合，后者等回合结束；队列支持修改、删除、重排与转为当前回合输入。其文档还写明，自动处理排队消息需要有连接中的 Project Editor，这一点与常驻本地服务的运行预期不同。[S8]

Lovable 当前默认 follow-up 在下一处自然停顿接入；部分旧账号仍保留队列。普通补充、问题答案以及某些工具条操作的处理时机不同，停止会保留已完成的工作。其页面对旧队列重新启用的描述存在前后差异，不能承诺对所有账号开放同一个开关。[S9]

Figma Make 允许生成期间继续输入，排队消息可重排、编辑或删除。[S10] ACP 则从协议上提供带会话与工具请求身份的权限选项，并要求取消回合时返回 cancelled；不能把一个请求的答案当成另一请求的授权。[S11]

### 对 GOGO 的建议

GOGO 已确定的“默认排队、显式中途插话”无需因竞品默认改变而翻转。应把已有能力表达得更可靠：默认发送按钮位置稳定；当前收件人、运行情况与送达方式在同一区域可见。能力不足时如实说明，不把“排队”改个名字就称为“立即插话”。

| 用户动作 | 直接结果 | 必须保留的边界 |
|---|---|---|
| 继续输入普通补充 | 按已显示的方式排队或发送 | 收件人、目标、附件一起绑定；不能切页后错投 |
| 选择中途插话 | 针对该席位当前回合送达 | 回合已变更时返回事实，不能偷偷转发到下一目标 |
| 撤回尚未开始的消息 | 取消该条待发送任务 | 已开始则不能声称成功撤回；撤回不是派发失败 |
| 点击停止 | 请求停止当前明确对象 | 停止请求已送出与实际停止分开；不自动撤销已改文件 |
| 回答 CLI 问题 | 答案返回原请求 | 原文、原选项、单多选规则、请求有效期不被产品改写 |
| 收起一个问题 | 让出阅读空间，保留待答记录 | 收起不等于选择默认答案，也不等于拒绝 |

多位 Agent 同时提出真实问题时，可在输入区附近显示简短的待答条目，点开一项在稳定位置作答，其他项不覆盖当前草稿。若上游没有跳过能力，界面就不创造“跳过并继续”；若请求已失效，就展示失效状态。普通模型工作问题与真实权限请求可以共享排版尺度，但必须保留各自含义。

**待验证：** 中文输入法按 Enter 不误发；问题到达不抢走正在打字的焦点；相同文字的两个不同请求不串答；撤回与启动同时发生时结果准确；停止主控是否包含仍运行的子任务必须由实际运行机制决定。

## 5. 成果怎样看，反馈怎样落到正确位置

### 已核对的事实

Lovable 新的预览工具条支持点选元素、直接编辑文字、圈画与评论；点选可以把多个元素作为引用附到主输入框。[S3] Bolt 的预览修改先进入暂存批次，保存时才由 Agent 更新代码；Figma Make 的属性调整也要 Apply 后才提交。[S4] [S12]

Figma Make 的评论会带当时元素状态的截图，并按当前版本与其他版本分组；它还区分给协作者的评论与交给 Agent 的修改标注。新编辑工具只适用于新 Make 文件，旧文件仍使用旧接口，不能用一张新截图推断全部文件都已升级。[S13] [S12]

### 对 GOGO 的建议

默认成果区应显示用户能判断的本体。网页是可操作预览，文档是排版内容，表格是数据与计算结果，脚本则是输入样例、运行结果和输出文件。代码 diff 与原始日志是进一步核查入口；通用地把所有成果换成文件路径清单，会把判断成本重新推给普通用户。

| 交互 | 建议表现 | 不能省掉的事实 |
|---|---|---|
| 指着网页说“改这里” | 进入选择模式，点元素，输入框出现引用，再自然语言描述 | 页面、元素/区域、截图、预览版本；选择模式不触发真实购买等页面动作 |
| 一次提出几处小改 | 多个标注收在一条草稿里，一次送交主控 | 每个标注有自己的位置与版本，不自动扩成独立任务 |
| 看旧版本 | 明显标为旧预览，允许对比 | 浏览不是恢复；旧反馈不能静默套到新布局 |
| 比较修改前后 | 相同页面、尺寸和必要场景数据下比较 | 不同用户态或数据造成的差别不应被误认为代码改动 |
| 给主控转一条旁聊 | 小范围引用与来源，送达状态就地显示 | 不搬整段聊天，不把审计的解释自动升级为 Owner 决定 |
| 源码变了但预览未更新 | 标出“预览正在更新”或“仍显示上个版本” | 运行身份需可核对，不能展示旧效果却标最新 |

从预览得到的 DOM 路径只能作为定位材料，不是永远有效的源码身份。跨版本找不到原位置时保留截图与原始描述，交给主控理解；不要硬贴到看起来相似的元素。

**待验证：** 用户能否不用报文件名就完成反馈；切换预览版本不会清掉文字草稿；点空白和 Escape 都能退出选中；已进入评论/选择模式时是否仍误触页面按钮；新版本里被删除的元素不会被错误重新定位。

## 6. 停止、失败、断线与恢复

### 已核对的事实

Claude Code 的恢复分别处理代码与对话；其文件快照不等同整个环境，命令修改、其他会话和多类子 Agent 改动不由普通 rewind 完整覆盖。[S14] Replit 的恢复文档则包含项目与对话，开发数据库是可选项，生产数据库不由该回退自动恢复。[S15] Bolt 提供先预览旧版本再恢复的路径。[S16]

三者表明：“回到刚才”至少可能指撤回一条消息、恢复聊天、恢复文件、恢复数据库，或恢复正在执行的现场。一个无范围的“撤销”会掩盖真正差异。Apple 要求操作名称和反馈能帮助人预判撤销结果；PAIR 强调失败后说明出路。[S6] [S17]

### 对 GOGO 的建议

| 事实 | 用户可见文案方向 | 后续行为 |
|---|---|---|
| 页面与服务断开 | “连接中断，最后更新于……” | 保留草稿和已有记录；先重新核对运行与送达事实 |
| CLI 已退出 | “执行已停止，已保存的改动仍在” | 显示已有成果；续接或新会话的区别按能力说明 |
| 消息是否收到未知 | “暂时无法确认是否送达” | 不自动重发可能已经执行的操作 |
| 额度明确不足 | “该席位暂时无法继续”并呈现真实来源 | 现有授权范围内由主控处理；不暗中换账号或加购 |
| 检查失败 | 人能读懂的问题与影响 | 详细错误可展开，主控继续处理已授权的修复 |
| 回退只能覆盖文件 | “恢复此版本的文件” | 同时列明不恢复的内容，不能称整个现场已经回到过去 |

取消应有明确对象。当前回合的停止、整件工作的停止和暂停未来派发可能是不同操作，只有底层能可靠执行的动作才可以出现。普通停止不应再强制填写理由；对真实不可逆后果仍应遵守既有权限边界，但不由应用凭空生成第二套业务审批。

**待验证：** 窗口关闭/重新打开后的原始运行身份；发送后断线是否重复派发；停止确认前按钮是否误显示已完成；源码和数据库分开恢复后的说明；外部写入发生后是否仍错误声称全部可撤销。

## 7. 团队交接与审计

Linear 区分原始用户输入和 Agent 的动作、问题、回复、错误，并能把临时活动替换为下一条活动。其 session complete 仍是运行结束状态，不是 GOGO 的 Owner 验收。[S18] Cindy 的 Review 则通过实际配置清除会话续接和记忆继承，这是此前源码研究中可借鉴的独立性机制。[S19]

建议把交接记录附在原工作里：谁接手、拿到哪些任务边界、核对哪个版本、交回什么。用户看主控结论，必要时展开原始证据。施工和审计的完整私有会话不应成为用户每次必须阅读的材料。

审计结果必须绑定成果版本。若通过后文件又发生相关改动，旧结论继续保留为历史，当前成果需要重新确认适用性；界面不能继续无条件挂同一个“通过”。设计审计、计划审计与代码审计的被审对象不同，不能用“审计完成”一句话抹掉对象差异。

旁聊审计席可以是普通咨询，正式独立审计需要对应的干净会话和证据路径。当前 GOGO 按席位复用原生会话的缺口已在[上下文研究](context-map.html)记录，本次没有重跑正式审计或改变底层实现。

**待验证：** 施工回执中的路径能否精确定位；审计是否读取正确候选；审计后修改是否使结论过期；Owner 改目标后主控能否把变更送到受影响的执行者，而不改变无关任务。

## 8. 花费与权限的表达

直接操作外观不一定是免费的本地动作。Bolt 与 Figma Make 的预览属性编辑在应用到代码时会调用 Agent；Lovable 的不同工具条动作也有不同计费条件。[S3] [S4] [S12] Replit 文档把部分费用挂在已完成请求旁，同时注明账单页有延迟；讨论路径也可能计费。[S20]

对 GOGO，金额、token 用量、订阅额度和预算限制应保留来源及范围。CLI 没报就标未知；估算不能伪装成实付金额。收件人菜单可提供足够的模型/实例信息供选择，详细用量放到工作或实例详情，不让主输入区堆满技术指标。

权限请求应显示真实操作对象和上游给出的有效选项。ACP 的 allow_once 和 allow_always 是不同语义，产品不能自行把后者缩窄或扩大成项目权限。[S11] 展开路径与风险说明可以帮助理解，但不更改原选择；真实登录继续发生在用户能看到的官方界面，凭据不进入聊天正文。

**待验证：** 一次动作的花费提示是否出现在提交前或来源可用时；缺少 usage 的回合不记成零；默认值与当前运行配置分开；拒绝一个权限请求是否被错误记成整个项目失败。

## 9. 首次使用、信息密度与可达性

Apple 的 onboarding 建议在操作中教学、推迟非必要设置，并让独立教程可以跳过。[S21] 对 GOGO，第一次进入可以先看到一件示例工作、对话和成果，再在真实使用某项能力时说明需要哪种连接。已登录工具可以作为选择候选，但不能为了降低门槛就未经授权自动绑定、登录或发测试消息。

信息应按阅读目的分配空间：主要区域保留用户意图、模型回复、真实问题与成果；过程默认折叠到简短活动行；诊断放详情；需要 Owner 回答的事件才占注意力。Linear 的 Inbox 可借鉴“需要关注”和“普通更新”的分离，不必照搬一整套通知中心。[S7]

Apple 区分可量化与不可量化的进度，要求位置稳定、文字准确。[S22] 对多 Agent 工作，轮数不是完成百分比，进程活着也不能推导“完成了 80%”。有真实步骤进展时展示步骤，没有时展示正在做的事与最后一条可信更新。

画布不能只依赖拖动。W3C 对拖动功能要求提供不需要拖动的单指针替代，除必要情况外；仅提供键盘方式也不能覆盖这条要求。[S23] 因而列表切换、适应画布、重置位置、可点击调整分栏等都值得验证。W3C 的状态消息要求也支持用不抢焦点的方式通知重要变化，而不是把整个工具日志设成强提醒。[S24]

**待验证：** 窄窗口与 200% 缩放；键盘操作与可见焦点；中文输入法；侧栏缩放不隐藏发送；新增回复不清草稿也不强滚阅读位置；状态颜色在色觉差异情况下仍可辨识。这里不宣称已通过完整无障碍验收。

## 10. 连贯的目标体验

以下是待验证的一个普通场景，不是所有项目的固定施工流程。

| 时刻 | 用户行为 | 默认看到什么 | 系统必须保留什么 |
|---|---|---|---|
| 找到工作 | 打开“商城首页改版” | 主控对话与最近成果 | 项目、目标、草稿与工作区身份 |
| 表达目标 | “商品卡太挤，帮我改清楚” | 自己的文字与引用 | 没有用户说过的约束不冒充确认决定 |
| 需要澄清 | CLI 真正发出问题 | 在稳定位置显示原选项 | 有效请求身份，未发答案草稿 |
| 开始执行 | 主控依项目规则安排 | 一条易读进展，可展开团队 | 真实的任务与权限范围 |
| 中途补充 | “价格别改” | 排队/插话的明确回执 | 目标、收件人与当前回合 |
| 查看效果 | 打开预览，点价格区 | 选中区域与反馈输入 | 预览版本、截图、定位信息 |
| 看审计意见 | 查看主控总结 | 问题、影响、相关成果 | 审计对象、独立会话与证据 |
| 再次打开 | 回到同一工作 | 当前事实及已有成果 | 不把重连或重启当成重新执行授权 |

可操作的[场景检查器](work-paths.html#lab)展示三个窄交互：排队/撤回、绑定旧版本的反馈、断线后核对送达。检查器只改变自身示例状态，不控制 GOGO、文件、账号或真实模型。

## 11. 样例验证清单

所有条目当前均为**待验证的产品行为**。场景检查器只能验证呈现逻辑，不能替代真实 Provider、服务端并发或用户测试。

| 编号 | 设置与动作 | 成功条件 |
|---|---|---|
| U01 | 两件工作分别留草稿，来回切换 | 文字、附件、收件人各自保留 |
| U02 | 新目标继续使用同一主控席 | 如实表达会话连续性，不假称空上下文 |
| U03 | 施工运行中排队，再撤回 | 该任务未开始；原消息标已撤回；没有派发失败卡 |
| U04 | 回合结束边界同时点击插话 | 按实际回合归属处理，不跨目标 |
| U05 | 两席同时发相同题目 | 每个答案只回原请求；切题保留草稿 |
| U06 | CLI 没有跳过选项 | UI 不自动补出跳过/默认继续 |
| U07 | 中文输入法选词按 Enter | 不意外发送或提交答案 |
| U08 | 选择旧预览元素，随后出现新版本 | 草稿保留，反馈仍标旧版本，定位不被暗换 |
| U09 | 在选择模式点页面提交按钮 | 只选择，不提交真实表单；退出选择后正常操作 |
| U10 | 服务器收到消息但浏览器丢回执 | 重连核对原任务；不重复派发 |
| U11 | 点击停止但上游尚未停止 | 先显示停止请求，直到收到实际停止事实 |
| U12 | 代码回退但存在外部数据库修改 | 不宣称数据库、外部副作用一起恢复 |
| U13 | 审计通过后修改被审代码 | 旧结论标明对应旧成果，不直接继续当前通过 |
| U14 | Provider 没返回用量 | 未知有明确标记，不显示零花费或推断余额 |
| U15 | 点击看板空白、缩放、切列表 | 取消选中可达；布局不改变任务状态 |
| U16 | 不拖动，仅点击或键盘调整视图 | 仍能定位对象、调整布局与发送 |
| U17 | 200% 缩放或窄分栏下回答问题 | 文案可读、焦点可见、答案与发送不被遮挡 |
| U18 | 初次使用者完成一次反馈任务 | 能解释“改哪里、发给谁、是否开始”；不需术语辅导 |

U18 必须由真实目标人群验证。自动化点击或 Agent 自己觉得简单，只能证明交互可执行，不能证明普通人容易理解。记录任务完成情况、误操作、求助点和用户对当前状态的解释；本次没有采集真人测试数据。

## 12. 设计取舍与剩余未知

可推进的设计方向是：项目/工作作为稳定入口；成果预览作为第一类内容；团队和过程按需查看；输入和请求位置稳定；反馈携带版本；恢复与计费按实际能力表述。无需为了模仿竞品新增通用工作流引擎、自动审批层或整套新的状态机。

几项不应机械引入的做法是：Replit 的项目级共同发布；Lovable 的 follow-up 默认；云产品的支付确认流程；“完整环境一键回退”的笼统承诺；将自动生成的计划步骤当成项目合同；让每位内部 Agent 都变成用户要维护的独立工作入口。

剩余未知集中在实际适配而非视觉装饰：各 CLI 当前版本的原生提问与停止能力；后台断开后的排队语义；同席位跨目标的记忆；预览版本和源码版本的一致性；真实用户在长任务里能否正确理解界面。源码、协议、官方文档分别只能支撑各自范围，应在后续产品验证中针对这些点补证据。
