# 项目上下文：怎么共享，怎么隔离

**产品范围说明：GOGO 面向多种成果生产，软件施工与通用生产两套模式并行。软件模式保留 Git、diff 和测试等既有要求，通用模式采用对应成果的审查依据；共用基础交互，允许同项目协作。完整方向见[改版研究总图](revision-map.html)。**

2026-09-13 · 五家产品固定源码快照 + GOGO 当前工作树的只读研究。以下方案是产品建议，不是已实现能力，也不把设计、计划、审计顺序定成所有项目的固定流程。

**项目共享资料，主控保持全局理解，执行者按任务拿材料，审计者从独立会话核对同一份成果。** 用户不应该替系统搬运整段聊天，也不应该被要求先理解一套上下文配置才能开始工作。

这里的“共享”首先是可查阅；只有明确送入提示词的内容才算本次输入，只有可核实的工具事件才可以标成已读取。模型是否理解、是否仍完整保留，不能由文件存在或一个绿色标记证明。

## 一、五家产品实际上怎么做

| 产品 | 共享什么 | 隔离什么 | 需要注意的边界 |
|---|---|---|---|
| AionUi | Team 的公共工作目录；团队任务与消息协作 | 每个成员关联自己的 conversation | 当前创建界面明确传 `workspace_mode: shared`。类型里虽然有 isolated，但不能凭这个枚举就宣称界面已经支持成员独立工作树或安全沙箱。底层 AionCore 的完整隔离实现本轮未验证。[A1][A2] |
| Cindy | Maker Memory 按工作目录划分；同一仓库 worktree 的对应子目录映射到同一记忆范围 | 不同子目录仍是不同范围；远端由主机身份 + 路径区分；Review 关闭 Maker Memory、清除原生会话续接参数 | 文件副本隔离和知识复用可以同时存在。Review 的独立性需要实际关闭继承，不能只换一个角色名字。[C1][C2][C3] |
| Orca | 原生 CLI 项目规则文件；可配置的共享依赖目录 | 每项任务的 worktree、分支、文件和终端 | 共享目录可能是符号链接，会重新连通部分文件；复制与链接不是同一件事。worktree 防止日常改动互踩，不是阻止任意文件读取的安全边界。[O1][O2] |
| Herdr | 通过 prompt、终端读取和显式消息交接协作 | 独立终端中的 Agent 进程；工作区/页签/面板用于组织 | 提供运行与控制原语，没有在所查机制里证明一个统一的项目知识库。把面板移动到另一工作区，也不等于清空其进程上下文。[H1] |
| Vibe Kanban | 同一 workspace 的文件与 Git 状态 | 每个 session 的聊天历史、进程 | 新会话看得到改动，不自动知道另一会话收到的指令。它清楚地区分了“共用文件”和“共用聊天”。此处是固定版本的本地机制研究，不是对其历史云服务可用性的声明。[V1] |

最适合 GOGO 借鉴的是：Vibe 的文件/会话区分，Cindy 的记忆范围和 Review 断开继承，以及 Orca 的明确工作副本。AionUi 的团队关系适合表达“谁正在接手”，不应因此把全队聊天广播给每个人。

## 二、GOGO 应该共享什么

| 内容 | 建议共享范围 | 怎样交到下一位手里 |
|---|---|---|
| 项目目的、约束、术语、现有设计与代码 | 这个项目内，需要这些资料的成员 | 引用原文件/原消息，保留来源；稳定资料可按需读取 |
| Owner 已确认的决定 | 本项目；必要时限定到一个目标 | 记录决定的具体范围和来源。草稿、自述、建议不能自动升级为已确认规则 |
| 当前任务 | 主控和本任务执行者 | 目标、允许修改范围、禁止事项、相关资料、成功条件；不附带整段历史 |
| 施工成果 | 接手者与审计者 | 精确版本、改动文件、原始测试证据、已知问题；简短说明附在证据旁 |
| 正式审计 | 审计者拿任务标准与被审版本；主控拿回结论与证据 | 新的模型会话，不继承施工会话；施工解释可以标为待核实的主张 |
| 个人偏好 | 用户明确希望跨项目复用时 | 与项目决定分开；“喜欢中文回复”可以跨项目，“这个 API 不能改”不应成为全局记忆 |

不同 CLI 的原生记忆格式、规则发现和历史压缩方式不同。跨模型交接可搬运的是材料、明确输入与可见记录，不能宣称完整搬运了另一模型的内部上下文。放一份 AGENTS.md 或 CLAUDE.md 在目录里，也不能单凭文件名声称所有厂商都已经加载。

**设计、施工计划是项目资料的两类成果，而不是产品强制的两个阶段。** 某项目可以要求设计先审、计划再审，另一个项目可以用一次短任务说明；主控依照该项目已确定的要求组织它们。

## 三、隔离必须分开检查

| 边界 | 需要做到什么 | 什么不能作为完成证据 |
|---|---|---|
| 项目之间 | 默认不自动引入别的项目的消息、记忆、目录或权限；显式引用时带来源 | 侧栏换了项目名称 |
| 任务之间 | 执行会话只得到自己需要的材料；主控可以有意保持项目级连续性 | 聊天列表按目标过滤 |
| 旁聊与主聊 | 转发只带选中的回复、必要背景与来源，不搬整段私聊 | UI 没显示旁聊历史，就推断同一席位的原生会话也不知道 |
| 写入之间 | 共用目录时协调写入；并行修改互有影响时才隔离副本并明确合并 | 新建两个聊天窗口，或只有一段“不许改”的提示词 |
| 施工与正式审计 | 独立模型会话、可核对的同一候选版本；权限由实际 Provider 能力约束 | 换了模型、角色叫 auditor、或者自称独立 |
| 账号与会话 | 账号提供调用身份；运行实例、原生历史和记忆另有范围 | 换账号等于清空上下文，或同账号等于共享所有对话 |

这些是不同种类的边界，不需要做成六组开关。尤其不能提供一个“完全隔离”总开关，却只是改了 cwd。工作区约束、只读策略和操作系统级隔离能保证的范围不同，要按实际机制描述。

审计问答与正式独立审计也应区分：日常旁聊可以续接会话；正式审计要另起干净会话。二者可以由同一审计席承担，但不能默认共用同一份历史并仍标成 fresh。

## 四、当前 GOGO 已经做到哪里

以下依据 **main HEAD 429bbce + 当前未提交工作树**。是源码路径核查，不是本轮真实 CLI 会话测试；当前工作树仍含暂停中的开发，不能当成已验收版本。

| 已查路径 | 当前实际机制 | 可以得出的结论 |
|---|---|---|
| `server.ts:2159–2264`、`projects.ts:237` | 切项目先关闭运行席位，再切换 dataRoot、seats、rooms、timeline、halt 状态；正在执行时限制切换 | 项目有应用数据边界和进程切换路径。若仍使用同一个实例目录，原生磁盘记忆是否跨项目读取还取决于 CLI，不能声称已彻底消除 |
| `server.ts:1211–1212` | `seats.get(id)` 命中就复用，键是席位 id | 在席位没被关闭/重建期间，换目标不会自动建立新原生会话 |
| `seat-runtime.ts:448–529` | Codex 启动时创建一个 thread，后续 turn 使用同一个 threadId | 上一条复用判断有适配器层支撑；conversationId 是消息归属，不能据此推断模型记忆隔离 |
| `server.ts:1498–1506` | 本轮明确拼接角色提示、运行说明、房间、工作区与 HEAD、用途限制和 body | 该公共装配点没有把整条 timeline 自动拼进提示词；也没有保证每个普通派发都含完整目标锚点与成功条件 |
| `server.ts:1640–1660` | 接力消息带 commit/涉及文件及上一席的任务文字，并提示独立读仓库 | 交接已偏向成果引用，但仍含上一席自述；材料可被读取不等于接收方已读完 |
| `server.ts:1727–1730` | 对账显式送目标锚点、checkpoint、当前 HEAD | 对账输入有具体版本依据，但最终仍调用同一席位复用路径；本轮未发现“每次正式审计新建原生会话”的保证 |
| `server.ts:3248–3286` | 旁聊转主控带选中回复正文，记录源卡；立即插话校验当前目标 | 有显式转发路径；不应把“没有转发”描述为原生审计席的历史被隔离 |
| `server.ts:754–811, 1400–1456` | 已存在共享工作区写入协调，席位使用同一 `config.workspace` | 当前并非完全无写锁，但这也不是“每个目标一个独立文件副本” |
| `server.ts:1240–1344` | 可绑定独立实例目录；本机 CLI 是明确的例外；实例同一时刻只给一个席位 claim | 实例独占不等于项目独占，HOME 隔离也不等于目标会话隔离 |

**最重要的缺口是：目前 UI 中的“目标/房间边界”，比原生会话的隔离边界更细。** 这不证明已经发生某次错误串话，但足以说明不能在界面上承诺“新目标就是干净上下文”。主控跨目标保持项目理解可以是有意设计；施工会话与 fresh 审计是否也这样复用，需要分别处理。

## 五、用户在界面里应该看到什么

项目标题旁放一个轻量的 **“项目资料”** 入口，打开侧面资料栏，不把上下文塞进全局设置的大表单。

| 位置 | 默认呈现 | 展开后才看 |
|---|---|---|
| 项目资料栏 | 资料名称、用途、来自哪里；项目已经确认的决定 | 文件路径、版本、原始消息、适用范围 |
| 当前对话底部 | 有明确附件/引用时，一行“本次引用 · 设计方案 · 任务说明” | 哪些内容已加入本次输入，哪些只是可查阅；不能无证据显示已读取 |
| Agent 接手记录 | “施工接到了什么”“审计在核对哪份成果” | 精确材料与版本、派发原文、真实会话身份 |
| 项目设置 | 项目文件夹、额外允许引用的资料目录、项目规则来源 | 更细的范围与原生 CLI 生效说明；已有机制支持后才接入控件 |
| 全局设置 | 跨项目的语言/表达偏好、账号与运行实例 | 与项目规则分开，不在这里存业务项目的决定 |

普通用户说“按这个设计继续做”，主控负责选中对应材料并交接；用户想核实时点开看依据。删除一个“本次引用”只影响尚未发送的输入，不能假装删除了模型先前收到的内容。

不新增自动弹出的业务选择题、阶段确认卡或强制配置向导。对话中的选择题仍只来自 CLI 的真实请求。资料查看、附件选择与来源展开是直接操作，不是系统代替模型编出来的决策。

## 六、一个完整例子

Owner 在“商城改版”项目里确认设计 v3。主控继续保留项目讨论，给施工 A 交付“实现商品卡”的任务和设计 v3，给施工 B 交付“修搜索”的任务和搜索接口约束。A、B 不自动收到彼此全部聊天；需要配合时交接明确内容。

A 交回成果版本 a1 和测试证据。正式审计新起会话，读取设计 v3、A 的任务边界及 a1 的真实改动；审计发现带出处的问题，主控据此组织修复。Owner 旁聊问“为什么这块这么改”，选择转发一条回复后，主控才收到这一条显式转发。

若 Owner 随后改成设计 v4，正在审计 a1/v3 的会话不会神奇地更新已收到的输入；主控需要明确处理受影响的任务。界面应该标清资料版本，不能继续用“已同步”掩盖这一差异。
