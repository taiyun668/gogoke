# OpenCode 1.18.32 on Windows LPAC: root metadata path

Status: source review at gogoke `799cb02b`; no product run, CLI launch, alias, or ACL change. The retained original installed-candidate error is `EPERM: lstat '\\?\C:\'` before ACP `session/new` completed. This is not evidence of a failed model request or login.

## Fixed startup chain

Gogoke H launches pinned OpenCode as `--pure acp` with the canonical host-bound F worktree as process cwd (`apps/desktop/native-host/src/store/session_transport/launch.rs`: `cwd`, `verify_observed_cwd`, `launch.current_directory`). H also sends that path as ACP `session/new` cwd (`apps/desktop/native-host/src/store/product_database/v37_runtime.rs`). The failed worktree was on `C:`; the host's physical FileId binding remains authoritative.

The [tagged ACP command](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/opencode/src/cli/cmd/acp.ts) uses `effectCmd` without `instance: false` or a directory override. Its `--cwd` option does not change the [wrapper's initial `process.cwd()` → `InstanceStore.load`](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/opencode/src/cli/effect-cmd.ts). [InstanceStore](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/opencode/src/project/instance-store.ts) immediately calls `FSUtil.resolve`; [that resolver](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/core/src/fs-util.ts) calls `realpathSync` first and catches only `ENOENT`, so `EPERM` propagates. `OPENCODE_DISABLE_PROJECT_CONFIG` skips later local-config loading in the [tagged config loader](https://github.com/anomalyco/opencode/blob/v1.18.32/packages/opencode/src/config/config.ts). `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG_CONTENT`, and `--pure` likewise do not replace this initial resolution.

[Bun 1.3.14 Windows `realpathSync`](https://github.com/oven-sh/bun/blob/bun-v1.3.14/src/js/node/fs.ts) calls `lstatSync` on the drive root before walking the path. Its source says this JS path preserves SUBST spelling, whereas native realpath sees through it. OpenCode's `normalizePath` then calls `realpathSync.native`; Bun binds it to [`uv_fs_realpath`](https://github.com/oven-sh/bun/blob/bun-v1.3.14/src/runtime/node/node_fs.zig). Bun's [libuv pin](https://github.com/oven-sh/bun/blob/bun-v1.3.14/scripts/build/deps/libuv.ts) is `4dcfac4780d394e0dc2d3fb30335ca01b553eb46`; that [Windows implementation](https://github.com/oven-sh/libuv/blob/4dcfac4780d394e0dc2d3fb30335ca01b553eb46/src/win/fs.c) opens the directory and calls `GetFinalPathNameByHandleW(..., VOLUME_NAME_DOS)`. Microsoft defines that result as a [fully resolved final path](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfinalpathnamebyhandlew). A successful native call is therefore expected to restore physical `C:` from a SUBST alias; the actual LPAC result is **not measured**.

## Existing options and precedents

| Route | Fixed-version finding |
| --- | --- |
| `--cwd`, `OPENCODE_DISABLE_PROJECT_CONFIG`, `OPENCODE_CONFIG_DIR`, `OPENCODE_CONFIG_CONTENT`, `--pure` | Do not bypass the first `InstanceStore`/Bun root `lstat`; excluded for the original startup failure by source order. |
| Per-user DOS alias rooted at the *same* F worktree/FileId | No copy or broader file grant is inherent, but current H never passes an alias; [local DOS devices use token AuthenticationId](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/local-and-global-ms-dos-device-names), and LPAC visibility is unmeasured. Bun native likely restores `C:`. **Experimental, not mature.** |
| Existing host path/handle shim | A host identity handle does not replace Bun's own `lstatSync(path)`; no existing H translation covers this call. |
| External server, unconfined process, WSL/container, new CLI build | Changes the fixed local H/LPAC/CLI target or authority boundary; not eligible for this case. |

Targeted own-history searches found no Windows Bun/LPAC ancestor fix in GOGO PARTY, NaveHQ, LoomOS, or gogoke [`docs/research/`](2026-09-26-kernel-parts-harvest.md). NaveHQ's worker-local Linux/WSL `HOME`/XDG route is a different boundary. Current [Paseo notes](https://github.com/getpaseo/paseo/blob/main/docs/providers.md) describe daemon-owned OpenCode servers/config injection; [T3 Code notes](https://github.com/pingdotgg/t3code/blob/main/docs/internals/providers.md) describe a server per thread and distinguish tool policy from native sandboxing. [OpenCode Monitor](https://github.com/jacobjmc/OpenCodeMonitor) manages `opencode serve` via REST/SSE; [CodexMonitor](https://github.com/Dimillian/CodexMonitor) is its Codex-oriented predecessor. None of those inspected sources documents a Windows LPAC drive-root metadata solution.

## Next falsifier and decision

No proven mature no-ACL configuration was found for the pinned binary and required host-created `C:` F worktree. A bounded no-ACL candidate identified here is a per-user DOS alias to **that exact worktree/FileId**. One cloud Windows actual-product candidate can retain H's canonical F authority while passing the alias coherently as OpenCode process cwd and ACP `session/new` cwd, with alias collision/target/lifetime tied to the real child. Keep fixed CLI digest, instance home, LPAC token/capabilities and `--pure acp`; do not log in or send a prompt. Count success only on original fixed CLI `initialize` and `session/new` ACKs with the same physical F FileId and no `C:` ACL change. Alias invisibility, `lstat(C:\)` EPERM, or a path outside the bound F identity falsifies this candidate. A provider metadata/auth failure is separately inconclusive; `session/new` may inspect a model catalog but performs no model inference. A stand-alone Bun probe cannot substitute for this result.

If this candidate is falsified, the exact OpenCode-instance LPAC SID / `C:` object-only / non-inheriting `FILE_READ_ATTRIBUTES` grant remains a separate Owner-authorized possibility, with before/after ACL readback and automatic revoke at instance deletion. The ordinary current-user token has no `WRITE_DAC` on `C:` in the retained read-only AccessCheck; no ACL write or elevation has occurred, and applying that exact grant would require a separately authorized mechanism. Metadata access does not imply drive-root listing or write access; this review does not exhaust all conceivable no-ACL techniques.
