The page-reported thinking times observed after completion were High **3m 13s**, Extra High **3m 17s**, Medium **59s**, and GPT-5.6 Sol Pro **7m 17s**. These are UI thinking indicators, not precise send-to-result wall times. The pre-send composer explicitly showed GPT-5.6 and the selected tier each time. After completion it still showed the same tier, with no visible downgrade or limit notice. The UI did **not** expose a distinct per-reply served-model field in these trials, so exact backend model identity remains unverified. No GPT-6 Pro message was sent.

The reply model was checked read-only after the trials. Under each reply, the `Retry / Switch model` menu offered `Retry with 5.6 Sol` for WCS-01, WCS-02, and WCS-04, and `Retry with 5.6 Pro` for WCS-05. Those controls describe a *future retry*, not the existing reply's served model. The adjacent reply controls and current composer tier also did not identify the served model. No Retry action was clicked. All four actual reply models remain `unverified` in the ledger; a visible mismatch in a future task will instead block the requested tier.

The first trial sequence **violated the subsequently added serial-dispatch rule**. Local reservation-to-completion intervals overlap for WCS-01/WCS-02 and WCS-02/WCS-04. The four completed ChatGPT tabs were then closed; the browser inventory showed zero remaining ChatGPT tabs. The revised skill checks the browser inventory before opening and before Send, holds one active task in the local ledger until GitHub result confirmation, and closes its tab immediately after confirmation. This tab rule is instruction-level; the ledger enforces the task slot atomically. A simulated expired cooldown remained blocked without manual clearance, and a new process read the persisted cooldown. The Codex fallback agent independently confirmed the local gate behavior and noted that Owner notification is an instruction/flag rather than an automated message, while an already running reply is not mechanically cancelled. No actual OS reboot, suspicious-activity warning, or security verification occurred.

The in-app browser session remained signed in across multiple new, saved Chat conversations during this trial. Its expiry time was not measured; a single continuous session only proves a lower bound. No credential, account-usage number, or conversation URL is in this repository. The local ledger and trial event log live under `%LOCALAPPDATA%\gogoke\web-chatgpt-subagent`.

The legacy `trial_simulation` cooldown was explicitly cleared from the real local ledger at Owner direction. A Controller `reconcile` then recorded the current baseline: only skill and web construction seat messages from ledger start are counted; prior and Owner manual ChatGPT use remain unknown. New or lost state blocks Send until that local reconcile, without asking Owner for usage history. Future cooldown demonstrations must use a temporary state directory. Real security cooldowns still require 24 hours and a Controller safe-page observation, with no automatic resumption.

WCS-05's three high-risk findings were repaired: switched replies require a switch flag and charge both requested and actual tiers; a limit with no reply has a terminal `limit_no_reply` record; a new or lost ledger fails closed until reconcile; and task IDs are unique across seats, including released reservations. Each defect has a Windows test. After WCS-11, Owner directed that Luna perform browser steps directly rather than run a browser script. The browser script and its prepare/finalize wrappers were removed. Ledger calls now use `pythonw.exe` with `CreateNoWindow` and a private receipt; the watcher runs under `pythonw.exe` and starts its `gh`/`codex queue` children with `CREATE_NO_WINDOW`. Four Windows tests cover those processes and the PowerShell wrappers. Process tests alone cannot prove that no brief unrelated desktop window appeared. This trial does not imply the route is enabled.

WCS-12 supplies that live observation: the required ledger receipts and watcher startup receipt all recorded `console_window_present=false`, the running watcher had no main-window handle, and Owner reported no visible window or black-console flash during dispatch. The browser was a background IAB tab, not a page visible on Owner's screen. The manual Luna agent marked the GitHub-card tab for handoff before navigating to ChatGPT; despite that mark, the ChatGPT tab was absent at result confirmation. The skill now explicitly marks the ChatGPT conversation **after** Send. This timing correction remains to be retested. The WCS-12 review's two findings led to a wrapper change that throws on nonzero ledger status and to tests of the actual PowerShell wrappers; the tests do not run a live `codex queue` child, while the WCS-12 watcher did reach GitHub and queued a notice without a reported window.

For WCS-12, local Codex `token_usage_record` entries between dispatch start and ledger result confirmation (651.6 seconds, 10m 51.6s) show **Controller:** 34 requests, 5,816,376 input tokens including 5,800,320 cached, 5,327 output tokens; **Luna:** 36 requests, 2,329,494 input tokens including 2,264,064 cached, 12,924 output tokens. Each counted response ID was unique. Controller usage includes implementation and review work performed while the watcher ran, so this interval is not an isolated dispatch-overhead measurement.

The WCS-14 review's F1 observation is an intentional conservative bound: a switched send counts both the requested attempt and the actual served tier, while the requested tier is blocked until observed reset because provider-side charging is not visible. F2's demand for a known historical usage quantity conflicts with Owner's explicit baseline rule: start at the Controller's reconcile time, mark earlier and manual use unknown, and use visible downgrade/limit notices to stop a tier. F3 exposed a real gap: deleting `state.json` also erased the task-ID idempotency set. An append-only private `task-ids.jsonl` now retires IDs before a reservation is committed, migrates known IDs from existing state, and blocks reuse after state loss and reconcile. A Windows regression test covers that sequence. The subagent IAB tab still did not survive to result confirmation. A brief active-turn waiter was implemented and tested locally, then removed when Owner prioritized low Controller request count: Luna now ends after page dispatch, and the background watcher notifies Controller later. Result-time model inspection and tab closing remain unverified when the tab disappears on Luna exit.

OpenAI's [Terms of Use](https://openai.com/policies/row-terms-of-use/) say users may not “Automatically or programmatically extract data or Output.” They also prohibit circumventing rate limits or restrictions. The workflow reads GitHub artifacts as its result and stops at local caps, but the applicability of the extraction clause to automated UI model checks and dispatch requires Owner judgment before enablement. The [ChatGPT model-limit article](https://help.openai.com/en/articles/20001354-gpt-56-and-gpt-6-pro-in-chatgpt) documents possible fallback and says reset time appears when available; the trial did not deliberately exhaust an allowance.

The trial did not establish the web seat's exact account-wide remaining allowance, other Chat seat consumption before ledger initialization, unpublished tier limits, or a verified provider reset time. These remain explicit limits on cost comparison and formal route adoption. The WCS-05 review's lower-priority findings on reset chronology and recovery remain separate from the repaired F1-F3 defects. The skill's path was moved to `.agents/skills` based on the [current Codex skill discovery documentation](https://learn.chatgpt.com/docs/build-skills); the older `.codex/skills` path in fixed trial cards describes the already-executed historical commits.
