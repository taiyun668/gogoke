# Installed-product M2 V12 entry

Run `m2-sidechat-win11.mjs` with the signed Node runtime and a fresh private JSON config after Root has prepared the exact installed candidate, a private evidence directory, signed PowerShell/Python read-only observers, and two distinct pre-existing IDLE USER seats with their verified model settings. This entry owns only the new source and side worktrees/sessions. It does not replay M2 mainflow, use `EXCLUSIVE_M2_HISTORY_SEATS`, admit a prior claim, or declare acceptance.

The outer config uses the existing `ActualProduct` fields: `installed`, `version`, `sourceCommit`, `installedSha256` for `gogoke.exe`, `gogoke-native-host.exe`, and `resource-index.json`, `registryKey`, signed `pwsh` and `python`, `stateRoot`, `testbedSource`, `evidenceDirectory`, fresh `result`, `domainId`, `repositoryId: "gogokeSeatTestbed"`, original `instanceId`/`seatId`, and `observers` named `formal`, `memory`, and `ledger`. The formal observer must compare `formal`, `registeredFormal`, `formalData`, `formalRegistry`, and `shortcuts`. Credential values do not belong in config or evidence.

`sideChat` must contain `lifecycleOwnership: "EXCLUSIVE_V12_SOURCE_AND_SIDE"`, distinct Root-prepared `sourceSeatId`, `sourceTemplateId`, `sourceInstanceId`, `sourceWorktreeId`, `sideSeatId`, `sideTemplateId`, `sideInstanceId`, and `sideWorktreeId`, plus `sourceSeatSettings` and `sideSeatSettings` with the actual `model` and `effort` returned by those IDLE USER template seats. The entry rechecks each seat's USER layer, template, instance, model, and effort through the installed product and immutable reader. `ledgerEpoch` and `sourceCursor` must come from Root's current read-only native ledger observation; the entry checks both against its fresh `ledger` observer snapshot. They are never generated from a pin, default, or guessed value.

The runner creates and registers both new F roots, normally closes the candidate, and calls the existing `m2-readback.py ... side-worktrees` phase. The reader emits the two original registered physical identities in the existing `gogoke.37.private-m2-readback.v1` output. The candidate restarts; the runner then calls the unchanged `runSideChatCase` from `m2-sidechat.mjs`, supplying that artifact and an in-memory normal-restart callback. The original module opens/creates the source D conversation before it admits the side session. On success it stops and releases both H claims, normally closes the candidate, and invokes the existing reader's `final` phase. That phase checks the exact source/side H requests, receipts, StopFacts, releases and process custody; the real A turns and tool boundary; D create/question/lifecycle and source-ledger preservation; the authorized side file bytes; and the original F identities. Formal, memory, and ledger snapshots are compared around the run.

The reader's separate branch is selected only by `journal.entry === "m2-sidechat-win11"`; the default original M2 path and its child dispatch, merge, provider, and final assertions remain in force. Both phases retain the original journal schema `gogoke.37.m2-win11-e2e.v1` and output schema. Neither direct evidence nor a completed module result is V12 acceptance.

If an original request is uncertain or any step fails before the H StopFacts and releases are read back, the runner preserves the original journal and live session custody. It does not replay the request or force-stop the candidate. The Controller must use the retained evidence to decide the next authorized action; a caption close alone is not an H stop.

The allowed development check is signed Node `--check` on this entry. Actual Win11 execution, model use, login, candidate launch, and acceptance remain with Root.
